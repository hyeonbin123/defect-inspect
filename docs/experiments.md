### 분할 (결정적, `manifests/visa.csv`에 커밋)
정렬 키는 이미지 경로 문자열(예: `candle/Data/Images/Normal/0836.JPG`)의 SHA-256 16진수다.
- **정상 겹(fold)**: 범주마다 학습 풀 정상을 키 순으로 정렬해 순번을 5로 나눈 나머지를 겹 번호(0~4)로 준다
- **dev 결함**: 범주마다 학습 풀 이상 60장을 키 순으로 정렬해 앞 20장
- **라벨 풀**: 나머지 40장. 지도 학습의 k장은 여기서만 뽑는다. 시드 s의 순서는 `"{s}:{경로}"`의 SHA-256 순이고 k=5, 10, 20, 40은 그 순서의 앞에서부터 자른다(포함 관계)
- **dev 평가 세트** = 겹 0의 정상 + dev 결함 20장 (범주당 정상 60~121장, 이상 20장)

두 가지 절차(protocol)가 있다. 코드와 분석은 같고 데이터만 다르다.

| 절차 | 정상 풀 | 평가 세트 | 쓰임 |
|---|---|---|---|
| `dev` | 겹 1~4 | 겹 0 정상 + dev 결함 | 코드 점검, 구성 확인. 몇 번이든 돌린다 |
| `test` | 겹 0~4 (학습 풀 정상 전부) | 봉인 테스트 | 단계가 끝날 때 정해 둔 것만 한 번 |

`dev` 절차는 `test` 절차의 모든 분석(임계값 보정 비교 포함)을 봉인 테스트 없이 미리 돌려 보는 용도다.

### 전처리
- 원본(약 1,300~1,560 × 960~1,180px)을 가로세로 비율을 무시하고 정사각형 S×S로 줄인다: PIL `resize((S, S), BICUBIC)` (축소 시 안티앨리어싱 포함). S는 구성마다 정한다
- 픽셀 지표는 **모든 구성에서 256×256 격자**로 계산한다. 마스크는 0보다 큰 값을 결함으로 보고 PIL `BOX` 필터로 256×256으로 줄인 뒤 0보다 크면 결함이다(작은 결함이 축소로 사라지지 않게 함). 이상 점수 맵은 bilinear로 256×256에 맞춘다
- 입력 정규화는 백본의 ImageNet 평균·표준편차

### 지표
- **이미지 AUROC**: 범주별로 계산(동점은 평균 순위)하고 12개 범주의 단순 평균을 대표값으로 쓴다
- **AUPRO**: 범주별. 결함 영역(8방향 연결 성분)마다 겹친 비율을 구해 영역 평균을 내고, 정상 픽셀의 오검출률 0~30% 구간에서 적분해 0.3으로 나눈다. 12개 범주 평균이 대표값
- **픽셀 AUROC**: 보조
- **검출률 95%에서의 오검출률 (FPR@TPR95)**: 범주별로 테스트 결함의 95% 이상을 잡는 가장 높은 임계값을 잡고, 그때 틀리게 잡힌 정상 수를 12개 범주에서 합쳐 정상 전체 수로 나눈다(합산). 임계값을 테스트 라벨로 정하므로 운영 가능한 수치가 아니라 분리도의 요약이다
- **고정 임계값의 실제 오검출률·검출률**: 임계값은 범주별로 정상 점수만으로 정한다(아래). 오검출 수와 검출 수를 12개 범주에서 합쳐 비율을 낸다(합산). 범주별 수치는 보조로만 싣고 범주별 결론은 내지 않는다(범주당 결함 40장, 정상 200~402장)

### 임계값 보정
- 보정 점수 n개와 목표 오검출률 α가 주어지면 `l = ceil((n+1)(1-α))`, 임계값은 오름차순 l번째 점수. 점수가 임계값보다 크면 불량. `l > n`이면 최댓값을 쓰고 "보장 불가"로 표시한다
- 이론값: 보정 점수와 테스트 정상 점수가 교환 가능하면 실제 오검출률은 Beta(n+1-l, l)을 따른다. 범주 c의 오검출 수는 BetaBinomial(m_c, n_c+1-l_c, l_c)이고, 합산 오검출률의 95% 이론 구간은 범주별로 독립 추출한 합을 100,000번 모의(seed 0)해 2.5~97.5 백분위로 구한다
- 목표는 **α = 5%가 주**, α = 1%는 합산 수치로만 본다

### 신뢰구간과 판정
- 부트스트랩 2,000번(seed 0), 2.5~97.5 백분위. 범주 안에서 정상과 이상을 따로 복원 추출한다(층화). 두 방법을 비교할 때는 같은 추출을 써서 차이의 구간을 낸다
- 합산 비율의 구간은 같은 부트스트랩으로 낸다. 단일 비율을 이론값과 비교할 때는 Clopper-Pearson 95% 구간도 같이 적는다
- **"차이 있음"**: 차이의 95% 구간이 0을 포함하지 않고, 크기가 최소 효과 이상일 때만. 최소 효과는 이미지 AUROC 1.0%p, AUPRO 1.0%p, 합산 오검출률 2.0%p(α=5%) / 0.5%p(α=1%), 합산 검출률 2.0%p
- 구간이 0을 포함하면 "판정 불가", 0을 포함하지 않지만 최소 효과보다 작으면 "차이 작음"으로 적는다. 가설이 틀렸으면 틀렸다고 적는다

### 라벨 회계
- 비지도 방법은 **결함 라벨 0장**으로 정의한다: 구성은 문헌 기본값으로 미리 고정하고, 임계값은 정상 점수만으로 정한다. dev 결함으로 구성을 고르는 실험(4단계의 격자)은 "라벨 20장 사용"으로 적는다
- 지도 학습의 라벨 비용은 학습 k장 + 검증 20장(dev 결함)이다. 표에는 k와 k+20을 같이 적는다

## 1단계: 기준선 PatchCore와 임계값 보정 (규칙 2026-09-30)

### 구성 P0 (문헌 기본값으로 고정, 결함 라벨 0장)
- 백본: torchvision `wide_resnet50_2` (`IMAGENET1K_V1`), layer2와 layer3 출력
- 입력 256×256 (자르지 않음), fp16 추론
- 패치 특징: 각 층에 3×3 평균 풀링(stride 1, padding 1), layer3을 layer2 해상도(32×32)로 bilinear 확대해 이어 붙임 → 패치당 1,536차원, 이미지당 1,024패치
- 메모리 뱅크: 범주별. 탐욕적 k-center 코어셋 10%, 선택할 때만 128차원 무작위 투영(seed 0), 시작점은 seed 0으로 뽑은 패치
- 패치 점수: 뱅크에서 가장 가까운 패치까지의 유클리드 거리
- 이미지 점수: 패치 점수가 가장 큰 패치의 점수에 PatchCore 논문의 재가중(그 패치의 최근접 뱅크 패치의 이웃 9개 기준)을 적용
- 점수 맵: 패치 점수를 입력 크기로 bilinear 확대 후 가우시안 σ=4

### 구현 점검 (dev 절차, 판정 없음)
- 지표 코드는 scikit-learn 및 전수 계산과 대조하는 단위 테스트로 확인한다
- 직접 구현한 PatchCore와 anomalib의 PatchCore(같은 P0 설정)를 dev 절차의 같은 이미지로 세 범주(candle, macaroni1, pcb1)에서 비교한다. 이미지 AUROC 차이가 범주마다 2%p 이내여야 다음으로 넘어간다. 넘으면 원인을 찾아 적는다. anomalib은 `work/`의 별도 환경에 설치하고 이 비교에만 쓴다

홀드아웃에서 빼는 겹은 `test` 절차에서 겹 0, `dev` 절차에서 겹 1이다.

가설 (α = 5%, 합산 오검출률, test 절차):
- **H1** 재대입은 임계값이 낮게 잡혀 실제 오검출률이 목표의 두 배(10%) 이상이다
- **H2** 홀드아웃의 실제 오검출률은 95% 이론 구간 안에 있다
- **H3** 교차 적합의 실제 오검출률은 목표(5%)를 넘지 않는다. 겹을 뺀 뱅크는 전체 뱅크보다 작아 보정 점수가 조금 높게 나오므로 보수적인 쪽으로 치우친다고 본다
- **H4** 같은 목표에서 교차 적합(전체 뱅크)의 합산 검출률은 홀드아웃(겹 하나를 뺀 뱅크)보다 낮지 않다

판정:
- H1: 실제 오검출률의 95% 구간 하한이 10% 이상이면 지지, 상한이 10% 미만이면 기각, 그 사이면 판정 불가
- H2: 점 추정값이 이론 구간 안이면 지지, 밖이면 기각(밖으로 벗어난 방향을 적는다)
- H3: 95% 구간 상한이 5% 이하이면 지지, 하한이 5%를 넘으면 기각, 그 사이면 판정 불가
- H4: 검출률 차이(교차 적합 − 홀드아웃)의 95% 구간 하한이 −2.0%p보다 크면 지지, 상한이 −2.0%p보다 작으면 기각, 그 사이면 판정 불가
- α = 1%의 같은 수치를 나란히 적되 판정에는 쓰지 않는다

덧붙여 적는 것 (판정 없음):
- 보정 표본 수 n에 따른 실제 오검출률: 교차 적합 점수에서 n = 20, 50, 100, 200장을 1,000번씩 무작위로(seed 0) 뽑아 임계값을 정하고, 범주별 테스트 오검출률의 평균을 12개 범주에서 다시 평균한다. 비교 기준은 **같은 절차를 교환 가능한 점수에 돌린 모의**다: 범주마다 같은 크기의 보정 풀과 테스트 정상 집합을 균등 난수로 만들어 같은 함수에 넣기를 100번 되풀이하고(seed 0, 실현마다 300번 추출), 12개 범주 평균의 2.5~97.5 백분위를 기준 구간으로 삼는다. 관측값이 기준 구간 밖이면 표본이 유한해서 생기는 흔들림을 넘는 치우침으로 읽는다. Beta(n+1-l, l)의 평균은 참고로만 같이 적는다 (변경 기록 2)

### 지도 학습 (결함 라벨 k장 + 검증 20장)
- 특징: D-S와 같은 DINOv2 ViT-S/14 패치 토큰(448 입력, 32×32×384). 백본은 학습하지 않는다
- 헤드: Conv3×3(384→256)-BatchNorm-ReLU-Conv3×3(256→256)-BatchNorm-ReLU-Conv1×1(256→1). 패치 격자에서 결함 여부를 맞힌다
- 정답: 256 격자 마스크를 8×8 최대 풀링한 32×32
- 학습 데이터: 겹 1~4의 정상 + 라벨 풀에서 뽑은 결함 k장. k = 5, 10, 20, 40, 시드 0, 1, 2. 범주마다 따로 학습한다(12 × 4 × 3 = 144회)
- 손실은 BCE, 양성 가중치는 min(음성 패치 수 ÷ 양성 패치 수, 100). AdamW 학습률 1e-3, weight decay 1e-4, cosine 감소, 60에폭, 배치 32, 특징 격자 단위의 좌우·상하 뒤집기
- 검증: 겹 0 정상 + dev 결함 20장의 이미지 AUROC를 5에폭마다 재서 가장 높은 에폭의 가중치를 쓴다(같으면 뒤의 에폭. 변경 기록 4)
- 이미지 점수는 패치 로짓의 최댓값, 점수 맵은 패치 로짓을 256으로 bilinear 확대한 것(변경 기록 4)
- 임계값은 겹 0 정상의 점수로 정한다(홀드아웃)

### 가설과 판정 (test 절차, 12개 범주 평균 이미지 AUROC, 지도 학습은 시드 3개의 평균)
- **H5** k = 5와 k = 10에서 지도 학습은 기준 비지도보다 낮다. k마다 따로 판정: 차이(지도 − 비지도)의 95% 구간 상한이 0보다 작고 크기가 1.0%p 이상이면 지지, 하한이 0보다 크면 기각, 나머지는 판정 불가

읽는 법:
- **AUROC만 보면 놓친다(H9).** 이미지를 20~30% 어둡게 하면 P0의 AUROC는 그대로(+0.3, +0.5%p)인데, 고정 임계값의 오검출률은 4.0%에서 15.2%, 41.4%로 뛴다. AUROC가 그대로이고 검출률도 같이 오르므로(66.7% → 74.0%, 82.9%) 점수의 순서는 거의 그대로인 채 점수 전체가 위로 밀린 것으로 본다(점수 분포는 따로 재지 않았다). 순위 지표로 모델을 감시하면 이 고장은 보이지 않는다. 1단계의 "빼 둔 정상으로 잡은 임계값은 목표를 지킨다"는 촬영 조건이 그대로일 때의 이야기다
- **백본에 따라 무너지는 교란이 다르다.** 오검출률이 10% 이상인 조건은 세 방법 모두 8개이고, 그 가운데 6개(감마 1.5, 흐림 σ 1.0·1.5, 이동 4px, JPEG 70·50)는 같다. P0에만 밝기 0.8·0.7이 있고 D-S와 DM에만 이동 1·2px가 있다(D-S와 DM의 8개는 똑같다). DINOv2 특징을 쓰는 D-S와 DM은 밝기 배율 변화에 거의 반응하지 않는다(세 단계 모두 오검출률 변화가 정상 3,848장 중 4장 이하, ±0.11%p 안). 대신 위치가 조금만 어긋나도 무너진다. 256 격자 기준 1px 이동(448·392 입력에서 2px, 패치 크기 14px의 7분의 1)에 D-S는 31.9%, DM은 54.2%를 불량으로 판정한다. P0은 1~2px 이동에는 변하지 않았다(3×3 이웃 평균 풀링과 stride 8 이상의 CNN 특징이 이 정도 어긋남을 흡수하는 것으로 본다)
- 3-B(M2AD)에서 본 "D-S는 실제 조명 변화에 덜 무너지고 위치 변화에 더 무너진다"와 같은 방향이 VisA의 밝기 배율 교란과 이동에서도 나왔고, DM도 같은 쪽이다. 다만 VisA에는 실제 조명 변화가 없고, M2AD의 합성 감마 1.5에서는 D-S가 73.3%로 P0(53.3%)보다 더 무너졌다. 다만 M2AD에서 P0은 4px 이동에도 오검출률이 변하지 않았는데 VisA에서는 37.9%로 올랐다
- 흐림과 JPEG는 두 번째 강도(σ 1.0, 품질 70)부터 세 방법 모두 오검출률이 10%를 넘는다. 감마 1.5와 이동 4px도 세 방법 모두 넘는다. P0은 흐림 σ 1.0에서 정상 거의 전부(99.9%)를 불량으로 판정한다
- 실무로 옮기면: 어느 방법을 쓰든 고정 임계값은 촬영 조건(노출, 초점, 압축, 위치 맞춤)과 한 묶음이다. DINOv2 계열은 밝기 배율 변화에는 거의 반응하지 않지만(감마 1.5에서는 D-S 10.3%, DM 11.7%로 10%를 넘었고, M2AD 실제 조명에서는 D-S도 재보정 없이 57.6%였다) 지그와 위치 맞춤을 더 엄격히 해야 한다. WideResNet 계열은 반대로 밝기에 약하고 256 기준 1~2px 어긋남에는 버틴다

한계:
- 교란은 모델 입력 크기로 줄인 뒤에 줬다. 실제 노출·초점 변화는 센서와 렌즈에서 생기므로 이 교란과 같지 않다(3-B가 실제 조명 쪽 수치다)
- 이동은 가장자리 픽셀을 복제해 채운다. 어긋남과 함께 가장자리 몇 줄의 모양도 바뀐다
- DM의 임계값은 홀드아웃(1,158장), P0·D-S는 교차 적합(5,773장)으로 정했다. 방법 사이의 오검출률 비교에는 보정 방식 차이가 섞여 있다
- 구간은 이미지 단위 부트스트랩이고 조건 사이에서 이미지가 같으므로 조건끼리의 차이도 짝지어져 있다. 교란 강도 3단계는 미리 정한 것이고, 그 사이 강도에서의 모양은 재지 않았다

### 3-B. M2AD에서의 실제 조명 변화 (질문 3)
- 범주: Motor와 Bird. 내려받는 파일이 가장 작은 두 범주(13.9GB, 14.4GB)로 골랐고 성능을 보고 고르지 않았다
- 시점: 000, 120, 240 (같은 간격의 세 시점). (범주, 시점)마다 검사기를 하나씩 만든다: 6개
- 기준 조명은 I01이다. 뱅크는 학습 시편 30개의 I01 이미지 30장으로 만든다. 방법은 P0과 D-S(구성은 VisA와 같다). DM은 조건마다 다시 학습해야 해서 하지 않는다
- 임계값: 학습 시편 30개를 시편 이름의 SHA-256 순으로 5겹으로 나눠 교차 적합, 목표 5%
- 라벨: 정상 = 정상 시편의 이미지. 불량 = 불량 시편의 이미지 가운데 메타데이터의 `image_anomaly`가 1이고 `detectable`이 참인 것. 불량 시편의 나머지 이미지(그 시점에서 결함이 안 보이거나 판별 불가로 표시된 것)는 뺀다
- 조건: (S) 테스트 시편의 I01, (P) I01에 합성 교란 15조건, (R) 실제 조명 I02~I10 아홉 조건
- 지표: 검사기 6개를 합친 합산 오검출률(조건마다 정상 이미지 120장)과 합산 검출률, 검사기별 이미지 AUROC의 평균. 조건 S와의 차이는 시편 단위 군집 부트스트랩(2,000번, seed 0)으로 구간을 낸다: 범주 안에서 정상 시편 20개와 불량 시편 50개를 따로 복원 추출한다
- **H11** P0에서, 합성 교란 15조건 가운데 가장 큰 오검출률 증가(P − S)가 실제 조명 아홉 조건의 오검출률 증가(R − S) 평균의 절반보다 작다. "합성 최댓값 − 실제 평균의 절반"의 95% 구간 상한이 0보다 작으면 지지, 하한이 0보다 크면 기각, 그 사이면 판정 불가. D-S의 같은 수치를 나란히 싣는다
- 재보정: 새 조명 L(I02~I10 각각)에서, 학습 시편 가운데 n개(시편 이름의 SHA-256 순으로 앞에서 n = 8, 30)의 조명 L 이미지를 뱅크에 더하고(I01 30장 + 새 조명 n장), 임계값은 더한 이미지까지 넣어 시편 단위 5겹 교차 적합으로 다시 정한다. 그 뒤 조명 L의 테스트 이미지에서 오검출률과 검출률을 잰다
- **H12** P0에서, n = 30으로 재보정하면 아홉 조명을 합친 오검출률(정상 이미지 1,080장)이 10% 이하로 돌아온다. 95% 구간 상한이 10% 이하이면 지지, 하한이 10%보다 크면 기각, 그 사이면 판정 불가
- M2AD에는 공식 검증 분할이 없다. 코드 점검은 Motor의 시점 000 검사기 하나에서 조건 S와 I02만 돌려 본다. 전체 측정은 한 번 돌리고 장부에 남긴다
- 한계: 독립 표본은 시편이다(범주당 정상 20개, 불량 50개). M2AD는 작은 물체를 여러 시점에서 찍은 데이터라 VisA와 도메인이 다르므로, 결론은 M2AD 안에서만 말한다. I01~I10이 물리적으로 어떤 조명인지는 확인하지 못했다

### test 절차 (1회)
서빙 구성의 설정으로 `run_grid`를 test 절차에서 한 번 돌린다(세 비율, 뱅크 저장). 그 뱅크와 교차 적합 임계값으로 아티팩트를 만들고, onnxruntime CPU 파이프라인(FP32, INT8)으로 봉인 테스트와 교차 적합 풀을 다시 채점한다. INT8은 정적 양자화(QDQ, MinMax, 범주마다 dev 풀 정상 8장씩 96장으로 보정).

DINOv2 설정은 INT8 모델을 만들 수 없다(변경 기록 5). 서빙 구성으로 DINOv2 설정이 뽑히면 CPU 파이프라인은 FP32만 채점하고 H14는 판정하지 않으며 그 사유를 적는다.

### 가설과 판정
- **H13 (코어셋)** 서빙 구성의 설정에서 코어셋을 10%에서 1%로 줄여도 평균 이미지 AUROC는 1.0%p 넘게 떨어지지 않는다(test, torch 파이프라인). 차이(1% − 10%)의 95% 구간 하한이 −1.0%p보다 크면 지지, 상한이 −1.0%p보다 작으면 기각, 그 사이면 판정 불가
- **H14 (INT8)** FP32 CPU 파이프라인의 교차 적합 점수로 정한 임계값을 INT8 점수에 그대로 쓰면 합산 오검출률이 2.0%p 넘게 달라진다. 같은 추출로 낸 차이의 95% 구간이 0을 포함하지 않고 크기가 2.0%p 이상이면 지지, 구간 전체가 ±2.0%p 안이면 기각, 나머지는 판정 불가. INT8 점수로 임계값을 다시 잡았을 때의 오검출률을 같이 적는다
- **H15 (지연 예산)** 서빙 구성이 test에서 다음 셋을 모두 만족한다: (가) CPU 지연 중앙값이 장당 200ms 이하, (나) CPU FP32 파이프라인 자신의 교차 적합 임계값(목표 5%)에서 합산 오검출률의 점 추정값이 6% 이하(1단계의 이론 구간 상한 5.9%를 올림한 값), (다) 평균 이미지 AUROC가 2단계의 기준 비지도 방법보다 2.0%p 넘게 낮지 않다(점 추정값). 셋 다 만족하면 지지, 하나라도 어긋나면 기각하고 어느 조건인지 적는다
- torch 파이프라인(GPU fp16)과 CPU FP32 파이프라인의 점수 차이(상대 오차의 중앙값과 최댓값), torch 임계값을 CPU 점수에 그대로 썼을 때의 오검출률도 판정 없이 적는다

| H15 지연·오검출률·정확도를 모두 만족한다 | **기각** | (가) CPU 214.4ms > 200ms 불만족, (나) 오검출률 4.18% ≤ 6% 만족, (다) AUROC 90.04가 2단계 기준(dm, 96.79)보다 6.76%p 낮아 불만족. 어긋난 조건: (가), (다) |

H15 (가)는 test 뱅크로 만든 아티팩트(실제로 배포할 것)의 지연으로 판정했다. 이 읽기는 값을 재기 전(18:25)에 측정 스크립트에 적어 두었지만 커밋으로 남기지 않았고, 문서에는 측정 뒤 커밋(`28c1fbb`)에서 처음 적었다. 그때는 test AUROC(90.04)를 이미 본 뒤라 (다)가 어긋난다는 것을 알고 있었다. dev 뱅크의 지연(184.2ms)으로 읽어도 (다)가 어긋나므로 판정은 같다.

읽는 법:
- **CPU로 옮기는 것 자체는 공짜다.** onnxruntime FP32 파이프라인은 GPU fp16 torch 파이프라인과 AUROC가 같고(차이 −0.002%p), GPU에서 정한 임계값을 CPU 점수에 그대로 써도 오검출률이 4.18%로 같다. 이미지 점수의 상대 차이는 중앙값 0.012%, 최대 2.6%다
- **INT8은 이 구성에서 쓸 수 없다(H14).** 점수가 중앙값 24% 달라져 FP32 임계값을 그대로 쓰면 정상의 68%를 불량으로 판정한다. INT8 점수로 임계값을 다시 잡으면 오검출률은 3.77%로 돌아오지만 AUROC가 82.95로 7.1%p [5.1, 9.2] 떨어지고 검출률이 67.1%에서 49.0%로 준다. 속도는 이 측정에서 FP32보다 10%(214.4 → 191.3ms) 빨랐지만 그 절반은 정밀도와 무관한 최근접 탐색 시간의 흔들림(120.4 대 108.3ms)이고, dev 뱅크로 잰 값에서는 3%(184.2 → 179.2ms)였다. 최근접 이웃 거리로 점수를 내는 방법은 특징의 작은 오차가 그대로 점수에 실린다. MinMax 대신 백분위·엔트로피 보정이나 보정 장수 늘리기는 규칙에 없어서 시도하지 않았다
- **dev 뱅크로 잰 지연은 배포할 아티팩트의 지연보다 짧다.** 테스트 절차의 뱅크는 교차 적합 풀 5겹을 모두 쓰므로 dev(4겹)보다 25% 크다. 1% 코어셋에서는 최근접 탐색이 지연의 절반쯤이라 뱅크 크기만으로도 탐색이 약 84ms에서 105ms로 늘어 지연이 약 205ms로 계산되고, 실측은 214.4ms였다(탐색 120.4ms, p95 286ms라 나머지 약 9ms는 측정 때의 흔들림으로 본다). 예산 근처에서 구성을 고를 때는 배포할 뱅크 크기로 지연을 재야 한다
- **"CPU 200ms"의 값은 정확도 6.8%p다.** dev 지연으로 예산 안에 든 구성 가운데 dev AUROC가 가장 높은 것(배포용 뱅크로는 214.4ms)이 2단계의 Dinomaly(GPU)보다 test AUROC가 6.8%p 낮다. GPU가 있으면 같은 PatchCore도 11ms 안에 끝나므로, 예산을 지키려면 GPU를 두거나 정확도를 내주거나 둘 중 하나다. Dinomaly의 CPU 지연은 재지 않았다
- 코어셋 10% 행이 1단계 P0 test와 같은 수치라 격자 코드(`run_grid`)가 1단계 코드(`run_patchcore`)와 같은 점수를 낸다는 것도 확인됐다

한계:
- 지연은 pcb1 한 범주, dev 풀 정상 50장의 중앙값이다. 범주마다 뱅크 크기가 달라(test 뱅크 1% 기준 범주 평균 4,926행) 지연도 범주마다 다르다
- 지연 측정 직전 5초 CPU 사용률이 16.8%였다(직전 1분 평균 6.9%. 직후 1분 평균 3.4%는 콘솔 출력으로만 확인했다). 측정 중 부하는 기록하지 않았다
- INT8 보정은 규칙에 적은 한 가지 방식(QDQ, MinMax, 96장)만 시도했다

## 6단계: CPU 서빙용 Dinomaly ViT-S (규칙 2026-10-03, 측정 전)

4단계에서 규칙대로 고른 서빙 구성(PatchCore wrn50-256 코어셋 1%)은 H15가 기각됐다: 배포용 뱅크의 CPU 지연 214.4ms, test AUROC 90.04로 2단계 DM(96.79)보다 6.76%p 낮다. DM의 CPU 지연은 재지 않았다. 이 단계는 Dinomaly의 인코더를 ViT-S로 줄인 모델(DMS)이 CPU 200ms 안에서 서빙 PatchCore를 대체할 수 있는지 잰다. 메모리 뱅크가 없으므로 dev 뱅크와 배포 뱅크의 지연이 달라지는 문제(규칙 변경 6, 214ms 사례)는 생기지 않는다.

공통 구성 (2단계 DM과 다른 곳은 굵게):
- anomalib 2.6.2의 `DinomalyModel`. **인코더는 DINOv2 ViT-S/14 register 4개**(`vit_small_patch14_reg4_dinov2`, D-S와 같은 가중치. 새로 받을 것이 없다). 읽는 층 2~9, 융합 [[0~3], [4~7]], 디코더 8블록(선형 어텐션), 병목 dropout 0.2. 모두 구현 기본값이다

- **입력 크기를 고정해 위치 임베딩을 한 번만 보간한다.** 동적 경로가 이미지마다 부르는 같은 함수(anomalib가 antialias를 끈 bicubic)로 한 번 계산해 두므로 출력이 같다(테스트로 비트 단위까지 확인). 고정한 모델에 다른 크기를 넣으면 오류가 난다

### 관문 1: 학습 전 CPU 지연 (GPU 없음, 이 규칙을 커밋한 뒤 잰다)
- 지연은 가중치와 무관하므로 학습하지 않은 모델(seed 0 초기값)로 잰다. 모델은 ONNX(opset 18)로 내보낸다. 그래프는 정규화한 이미지 [1, 3, S, S]를 받아 이미지 점수와 256×256 맵을 낸다(맵 리사이즈, 흐림, 상위 1% 평균까지 그래프 안). 내보낼 때 torch와 onnxruntime의 차이가 점수 상대 1e-3, 맵 절대 1e-3 이하인지 확인한다
- 재는 법은 4단계와 같다: 범주 pcb1의 dev 풀 정상 앞 50장(입력 크기 캐시)을 한 장씩, 워밍업 5회 뒤 50회의 중앙값, onnxruntime FP32(스레드는 기본값), 1500×1000 사진을 입력 크기로 줄이는 시간을 더한다. 뱅크가 없으므로 범주와 무관하다
- 측정 조건은 규칙 변경 6과 같다: 시작 직전 1분 동안 전체 CPU 사용률 평균이 10% 미만. 크기마다 직전 5초 CPU 사용률과 시작 때 GPU 사용률(`nvidia-smi`)을 같이 적는다. 60분을 기다려도 한가해지지 않으면 그때 재고 조건을 수치 옆에 적는다. 한가하지 않을 때 잰 값으로 200ms를 넘은 크기는 한가할 때 다시 재기 전에는 빼지 않는다
- 잴 것: 252, 280, 294, 308과 CAR 두 개(dms-252-car, dms-280-car). 보조로 동적 INT8(onnxruntime `quantize_dynamic`, MatMul만, 가중치 QInt8)의 지연도 같이 잰다(판정 없음)

- 결과는 `reports/stage6/latency.json`(`dms-<크기>-untrained`)와 `reports/stage6/gate.json`에 남기고, 학습 전에 이 절 아래에 적어 커밋한다

### 관문 2: fp16에서 안전한 선형 어텐션
2단계에서 DM은 fp16으로 학습하지 못했다(15번째 스텝 NaN). 디코더 선형 어텐션의 합이 fp16 최댓값 65,504를 넘는다(`work/dinomaly_nan_probe_cpu.json`: fp32에서 q·kv 최대 58,860 → 89,101). 패치는 키 k를 토큰 수 N으로 나누는 것이다. 출력은 (q·(kᵀv)) / (q·Σk)라 N이 약분되어 수식상 같고, 합만 1/N로 줄어든다.
- **(가) fp32 대조 (CPU, 이 단계에서)**: dms-280, 사전학습 인코더, 같은 초기값에서 패치한 모델과 원본 모델을 비교한다. dev 풀(겹 1~4)의 학습 배치 순서 첫 배치 8장의 추론 출력(이미지 점수 상대 차이, 맵 절대 차이)과 학습 3스텝(배치 8, fp32)의 손실 상대 차이가 모두 1e-5 이하이면 통과. 통과하지 못하면 패치를 쓰지 않고 (나)는 아래 대안부터 한다
- **(나) fp16 학습 (GPU, 다음 단계)**: dms-280, 배치 16, 60스텝, seed 0, 실제 학습과 같은 배치 순서. 기준은 fp32 + 원본 어텐션이다. fp16 autocast + 패치 어텐션이 (1) 60스텝의 손실이 모두 유한하고, (2) GradScaler가 건너뛴 스텝이 0이고, (3) 10스텝씩 나눈 여섯 구간의 평균 손실이 fp32 같은 구간 평균과 상대 3% 이내이면 통과다. 통과하면 모든 후보를 fp16 + 패치로 학습한다. 실패하면 fp16 + 선형 어텐션만 fp32(autocast 끔)로 같은 검사를 하고, 그것도 실패하면 fp32(원본 어텐션, 배치 16)로 학습한다. 선택은 `gate.json`에 남고 학습은 `--precision-from`으로 그대로 읽는다. 브리프의 "손실이 fp32 곡선의 약 3% 안"을 한 스텝 단위가 아니라 10스텝 구간 평균으로 정한 것은 배치마다 손실이 흔들리기 때문이다
- 관문 (나)의 60스텝 시간과 VRAM으로 학습 시간을 다시 추정해 적는다. 1회 실행 6시간 이내(공통 규칙)를 넘을 것 같으면 학습 전에 멈추고 적는다

### dev 평가와 선택 (결함 라벨 20장 사용)
- 학습한 모델마다 dev 절차(겹 0 정상 1,158장 + dev 결함 240장)를 torch(GPU)에서 **fp32로** 채점한다(`--no-amp`, 학습이 fp16이어도). fp16 채점은 점수를 fp16으로 반올림해 동점을 만들고, 서빙은 FP32라서다. 평균 이미지 AUROC와 구간, AUPRO, FPR@TPR95
- **선택**: CPU 지연(관문 1의 값) 200ms 이하 가운데 dev 평균 이미지 AUROC가 가장 높은 것. 같으면 입력이 작은 쪽. CAR 모델도 후보다. dev 결함으로 고르므로 "라벨 20장 사용"이다
- CAR 효과는 같은 크기의 CAR 켬 − 끔 dev AUROC 차이와 짝지은 부트스트랩 구간으로 적고 판정하지 않는다. Dinomaly2 논문의 VisA 수치(96.23 → 97.42)는 Dinomaly2의 기본선에 CAR만 더한 ablation이라 완성된 Dinomaly 위에서의 증분이 아니다

### 봉인 테스트 (선택한 구성 하나만, 1회)
1. torch: `run_dinomaly eval --protocol test --allow-test --stage 6 --no-amp`(GPU fp32). AUROC, AUPRO, 픽셀 AUROC, FPR@TPR95를 잰다. 장부 `dms-<…>`
2. CPU: 학습한 모델을 ONNX FP32로 내보내고(위의 1e-3 확인 포함) `dinomaly_serving score --protocol test --allow-test --stage 6`로 겹 0 정상과 봉인 테스트를 onnxruntime CPU FP32로 다시 채점한다. 장부 `dms-<…>-onnx-fp32`. **판정은 이 점수로 한다**
3. 지연: 학습한 아티팩트를 관문 1과 같은 방법과 조건으로 다시 잰다(`reports/stage6/latency.json`의 `dms-<…>`)

### 가설과 판정
- **H16 (H15와 같은 형식)** 선택 구성이 test에서 다음 셋을 모두 만족한다: (가) 학습한 아티팩트의 CPU 지연(리사이즈 + 추론, FP32) 중앙값이 200ms 이하, (나) ONNX CPU FP32 파이프라인 자신의 홀드아웃 임계값(겹 0, 목표 5%)에서 합산 오검출률의 점 추정값이 6% 이하, (다) ONNX CPU FP32 평균 이미지 AUROC가 2단계의 기준 비지도 방법 DM(96.79)보다 2.0%p 넘게 낮지 않다(점 추정값, 94.79 이상). 셋 다 만족하면 지지, 하나라도 어긋나면 기각하고 어느 조건인지 적는다
- **H17** ONNX CPU FP32 평균 이미지 AUROC의 차이(선택 구성 − 4단계 서빙 PatchCore의 ONNX CPU FP32, 90.04). 같은 봉인 테스트 이미지에서 범주 안 층화 부트스트랩(2,000번, seed 0)으로 짝지은 95% 구간을 낸다. 하한이 0보다 크고 차이가 1.0%p 이상이면 지지, 상한이 0보다 작으면 기각, 나머지는 판정 불가

### 판정 없이 함께 적는 것
- 목표 5%의 검출률(홀드아웃 임계값, ONNX FP32)과 구간

## 7단계: 조명 변화 대응과 라벨 없는 변화 감지 (규칙 2026-10-04, 측정 전)

3-B에서 기준 조명 I01의 정상 30장으로 만든 검사기는 다른 실제 조명 아홉 가지에서 무너졌다. P0의 합산 오검출률이 96.9%(일곱 조건에서 100%), AUROC가 55~68이고, D-S는 재보정 없이 57.6%다. 새 조명의 정상 8장으로 사람이 재보정하면 3.5%로 돌아오지만(H12), 언제 재보정해야 하는지 라벨 없이 알 장치가 없다. 이 단계는 세 가지를 잰다.
1. 재보정 없이 새 조명을 견디는 두 방법: 이미지별 특징 중심화(E1), 여러 조명으로 미리 등록(E2), 둘을 함께(E3). 판정은 H18, H19
2. 라벨 없는 변화 감지: conformal p-value와 test martingale. 판정 없음
3. 경보 뒤 무라벨 이미지로 자동 재등록·재보정하는 폐루프. 판정 없음

6단계에서 CPU 서빙 모델로 Dinomaly ViT-S(dms-280-car)가 H16을 지지했다(서비스 교체는 아직 안 했다). 1의 결론은 PatchCore(P0, D-S)의 메모리 뱅크에 대한 것이라 서빙 모델로 그대로 옮겨지지 않는다. Dinomaly는 여러 조명을 등록하려면 다시 학습해야 해서 이 단계에 넣지 않고 아래 "다음 라운드 후보"로 적는다. 2는 점수만 쓰므로 모델과 무관하다.

### 후보 (P0와 D-S 각각)
| 이름 | 특징 | 뱅크와 임계값에 쓰는 조명 |
|---|---|---|
| E0 | 그대로 (3-B와 같다) | I01 |
| E1 | 이미지별 중심화 | I01 |
| E2 | 그대로 | I01 + 등록 묶음 (두 팔) |
| E3 | 이미지별 중심화 | I01 + 등록 묶음 (두 팔) |

- **이미지별 중심화(E1)**: 백본이 낸 패치 특징 [H, W, D]에서 그 이미지의 패치 평균 벡터(fp32)를 뺀다. 뱅크, 질의, 교차 적합 모두 같은 변환을 거친다. 학습하는 것은 없다(`backbones.CentredPatches`, 설정 `p0-c`, `d-s-c`). 이미지 전체에 고르게 걸린 밝기 이동을 지우려는 것이고, 제품 전체 색이 바뀌는 결함도 같이 지울 수 있다
- **조명 묶음(E2)**: I01을 뺀 아홉 조명을 두 자리 이름("02"~"10")의 SHA-256 순으로 늘어놓고 앞 4개를 묶음 A, 나머지 5개를 묶음 B로 한다(`m2ad.illumination_groups`). **A = I03, I07, I08, I09, B = I02, I04, I05, I06, I10.** 팔 A는 I01 + A로 등록하고 B를 못 본 조명으로 재며, 팔 B는 그 반대다. 그래서 아홉 조명이 모두 한 번씩 못 본 조명이 된다. 뱅크는 학습 시편 30개 × 등록 조명 이미지(팔 A 150장, 팔 B 180장)에서 코어셋 10%, 임계값은 그 이미지들의 시편 단위 5겹 교차 적합 점수로 정한 목표 5% conformal 임계값이다. 한 시편의 여러 조명 이미지는 같은 겹에 든다
- 나머지(백본, 입력 크기, 코어셋 10%, 재가중 k = 9, 맵 σ = 4, 시편 겹, 목표 5%)는 3-B와 같다. 검사기는 (범주, 시점)마다 하나씩 6개다
- 코드: `defect_inspect.run_m2ad_enrol`(`val`, `test`), 분석 `defect_inspect.analyze_m2ad_enrol`. 브리프의 "run_m2ad 확장"을 새 모듈로 했다(3-B 코드는 고치지 않았다. 교차 적합과 채점 함수는 그대로 가져다 쓴다)

### 검증 (봉인 없음, M2AD 학습 시편만, 결함 라벨 0장)
- 3-B의 시편 겹(시편 이름 SHA-256 순위를 5로 나눈 나머지)을 바깥 겹으로 쓴다. 겹 f마다 뱅크는 겹 f 밖 시편 24개의 등록 조명 이미지로 만들고, 임계값은 같은 이미지의 나머지 4겹 교차 적합 점수로 정한다(중첩). 겹 f 시편 6개의 열 조명 이미지를 그 뱅크로 채점해 그 임계값과 비교한다. 평가 시편이 뱅크에도 임계값에도 들어가지 않아 test와 구조가 같다
- **선택 지표: 못 본 조명의 합산 오검출률.** 검사기 6개 × 시편 30개 × 못 본 조명(E0·E1은 아홉 조명, E2·E3는 팔마다 못 본 묶음) = 후보마다 같은 1,620장이다. 등록 조명의 오검출률도 같이 적는다(판정 없음)
- **선택 규칙**: 방법마다 못 본 조명 합산 오검출률이 가장 낮은 후보. 같으면(오검출 수가 같으면) 단순한 쪽(E0 < E1 < E2 < E3)
- 학습 시편은 모두 정상이라 검증에서는 검출률을 볼 수 없다. 뱅크가 넓어져 결함까지 정상처럼 보이는 위험은 test의 가드(아래)로만 본다
- 구간은 참고로 범주 안 시편 30개를 복원 추출하는 부트스트랩(2,000번, seed 0)으로 적는다
- 결과는 `reports/stage7/val.json`과 이 절 아래에 적고, **커밋하고 push한 뒤에** 봉인 test를 읽는다

### 라벨 없는 변화 감지 (판정 없음, GPU 없음, 저장된 점수만)
- **p-value 두 가지** (점수가 클수록 이상이므로 새 점수가 클수록 p가 작다. θ는 (0, 1]의 균등 난수)
  - 귀납형: p = (#{c > s} + θ(#{c = s} + 1)) / (n + 1). c는 그 검사기의 보정 점수 n개다. P0·D-S의 VisA는 학습 풀의 교차 적합 점수, DM·DMS는 겹 0 홀드아웃 점수, M2AD는 학습 시편 30장의 교차 적합 점수(모두 임계값을 정한 그 점수)
  - 전도형: 스트림 자체의 순위. t번째 점수에 대해 p_t = (#{i ≤ t: s_i > s_t} + θ_t × #{i ≤ t: s_i = s_t}) / t. 보정 집합을 쓰지 않는다
- **마팅게일**: Vovk et al. 2021(arXiv 2102.10439)의 Simple Jumper 구조(베팅 전에 전체 자본의 J = 0.01을 함수들에 고르게 다시 나눈다)에 거듭제곱 베팅 함수 ε p^(ε−1), ε ∈ {1(걸지 않음), 0.5, 0.2, 0.05}를 쓴다. 자본이 1/δ = 100에 닿으면 경보, δ = 1%. 점수가 교환 가능하면 전도형 p-value는 서로 독립인 균등분포라 Ville 부등식으로 스트림 전체에서 경보가 한 번이라도 날 확률이 1% 이하다. 귀납형은 같은 보정 집합을 공유해 서로 독립이 아니므로 이 보장을 그대로 받지 못한다(스켑틱 지적). 교차 적합 점수는 보수 쪽으로 치우쳐 있어(1단계) 귀납형 p가 조금 커지는 쪽이다
- 베팅 함수와 J는 실제 점수를 보기 전에 합성 스트림(정규분포 점수, `work/di2/sim_martingale.py`, 로컬)으로 골랐다. 원래 Simple Jumper의 베팅 함수 1 + ε(p − 1/2)는 한 장당 자본이 최대 1.5배라, 점수가 크게 바뀐 합성 조건에서도 변화 뒤 경보까지 중앙값 18~24장이 걸렸다. 거듭제곱 함수 집합은 같은 조건에서 4~7장이었고(변화 전 구간이 20장뿐인 전도형만 21장), 변화 없는 합성 스트림 400장의 허위 경보는 0.28%(4,000개 중)였다
- **허위 경보율**: VisA 봉인 test의 저장된 점수(이미지를 다시 읽지 않는다). 범주마다 test 정상 전부(200~402장)를 무작위 순서로 늘어놓은 스트림 1,000개, 12개 범주. 결함 섞임 0/5/10%: 섞는 결함 수는 round(r / (1 − r) × 정상 수)이고 그 범주의 test 결함 40장이 상한이다. 방법은 P0, D-S, DM, DMS(dms-280-car, ONNX CPU FP32). 허위 경보율 = 경보가 한 번이라도 난 스트림의 비율. 설계 목표는 결함 섞임 0%에서 1% 이하다. 결함이 섞인 스트림의 경보는 "결함이 이어서 나오는 것도 변화로 잡는다"는 한계를 보여 준다(5% 결함은 생산 중의 정상 상태일 수 있다)
- **경보 지연** (변화 뒤 경보까지 본 이미지 수, 경보가 난 장 포함. 변화 전 경보(조기 경보) 비율, 변화 뒤 구간 안에서 경보가 난 비율, 지연의 중앙값과 90백분위. 경보가 끝내 안 난 스트림은 무한히 늦은 것으로 센다)
  - M2AD 실제 조명(P0, D-S, 3-B에 저장된 E0 점수): 검사기마다 I01 test 정상 20장(+ 섞인 결함)을 무작위 순서로 늘어놓고 이어서 조명 L의 정상 20장(+ 결함)을 늘어놓는다. 같은 시편이 두 조명에서 한 번씩 나온다. 결함 섞임 0/5/10%면 구간마다 결함 0/1/2장이다. 스트림 1,000개 × 검사기 6개, 조명 아홉 가지
  - VisA 합성 교란 15조건(P0, D-S, DM, 3-A에 저장된 test 점수): 범주마다 정상과 결함을 스트림마다 무작위로 반씩 나눠, 앞 절반은 교란 없는 점수로, 뒤 절반은 교란 조건의 점수로 늘어놓는다. 같은 이미지가 양쪽에 나오지 않는다. 스트림 200개 × 12개 범주
- 모든 무작위성(순서, 섞을 결함, θ)은 설정 문자열의 SHA-256으로 시드를 정한다. 두 감지기는 같은 스트림과 같은 θ를 쓴다
- `python -m defect_inspect.drift` → `reports/stage7/drift.json`. CPU 약 10분. 판정이 없고 저장된 점수만 읽으므로 이 규칙을 커밋한 뒤 바로 잰다

### 폐루프 자동 재등록 (판정 없음, P0, 봉인 test 실행 안에서)
- E0 검사기에서 새 조명 L(아홉 가지)마다, 경보 뒤에 들어온 무라벨 이미지 n = 20장을 흉내 낸다: 학습 시편 SHA-256 순 앞 20 − k개의 조명 L 이미지(정상)와, 조명 L에서 결함이 보이는(라벨 1) test 불량 시편 가운데 시편 이름 SHA-256 순 앞 k개의 조명 L 이미지. k = 0, 1, 2(결함 0/5/10%). 경보 시점은 위 변화 감지에서 따로 재고, 여기서는 경보 뒤 n장이 새 조명의 이미지라고 본다
- **강건 거르기(trim)**: 묶음 20장을 시편 이름 SHA-256 순위로 5겹으로 나누고, 겹마다 나머지 겹 이미지로 만든 뱅크로 채점해 점수가 가장 높은 ⌈0.2 × 20⌉ = 4장을 버린다. 남은 16장을 I01 뱅크(30장)에 더하고, 더한 이미지까지 넣은 교차 적합으로 임계값을 다시 정한다(학습 시편은 원래 겹, 섞인 불량 시편은 그들끼리의 SHA-256 순위로 겹). 대조로 결함 2장을 섞고 거르지 않는 팔(none, k = 2)을 둔다
- 지표: 조명 L의 test 정상 120장(아홉 조명 합산 1,080장)의 오검출률, 등록에 쓰인 불량 시편을 뺀 조명 L의 검출률, 섞인 결함 가운데 거르기가 버린 수. 3-B에서 사람이 라벨을 보고 한 재보정(n = 8: 오검출률 3.5%, 검출률 42.2%, n = 30: 4.4%, 62.4%)을 참고로 옆에 적는다(절차와 장수가 달라 직접 비교는 아니다)

## CPU 런타임 대조: OpenVINO 대 onnxruntime (규칙 2026-10-04, 측정 전)
검사 서비스의 모델 dms-280-car(6단계)는 onnxruntime 1.30.0 CPU(FP32, 스레드 기본값)로 돈다. 같은 ONNX 파일을 OpenVINO 2026.4.1 CPU로 돌리면 점수가 같으면서 더 빠른지 잰다. dev 전용이고 봉인 테스트는 읽지 않는다. 6단계 수치와 서비스는 그대로 둔다.

근거가 엇갈린다. arXiv 2607.11356(2026-07)은 CPU에서 OpenVINO가 가장 빨랐다고 하지만 장비를 밝히지 않았고(Intel로 보인다), AMD CPU에서는 onnxruntime이 같거나 낫다는 안내도 있다. 이 PC의 Ryzen 5 3600(Zen 2)은 AVX2만 있고 AVX-512·VNNI·AMX가 없다. 결정의 쓸모도 작다: 서빙은 이미 149.7ms로 예산 200ms 안이고, 더 빠른 런타임은 더 큰 입력(예: 308px + CAR. 학습하지 않았고, 학습 전 308px 지연 197.5ms는 부하 상태 값이다)이 200ms 안에 들어올 수 있는지에만 영향을 준다. 그래서 빠른 팔이 나와도 이 항목에서는 런타임을 바꾸지 않고 후보로만 적는다.

### 팔
| 팔 | 런타임 | 설정 |
|---|---|---|
| R0 | onnxruntime 1.30.0, CPUExecutionProvider | intra-op 스레드 기본값(물리 코어 수 6). 지금 서빙 설정 |
| R1 | onnxruntime 1.30.0, CPUExecutionProvider | intra-op 스레드 12(SMT 포함). 대조 |
| R2 | OpenVINO 2026.4.1, CPU | `PERFORMANCE_HINT=LATENCY`, `INFERENCE_PRECISION_HINT=f32`, `NUM_STREAMS=1`, 나머지 기본값 |

- 세 팔 모두 같은 파일 `artifacts/dms-280-car/model_fp32.onnx`(sha256 `3bcf8e04…`)와 같은 전처리(`inspector.preprocess`)를 쓴다. OpenVINO는 ONNX 파일을 직접 읽고(변환한 IR 없음), `ReconstructionInspector`에 세션 대신 끼운다(`runtime_compare.OpenVINOSession`). 코드는 `src/defect_inspect/runtime_compare.py`
- onnxruntime의 transformers 최적화(그래프 융합)는 팔에 넣지 않는다. 계획 단계의 탐색에서 이 그래프의 Attention을 융합하지 못했고 2~5% 느렸다(규칙 밖의 탐색이라 수치를 기록으로 쓰지 않는다)
- OpenVINO는 새 의존성 그룹 `openvino`(`openvino==2026.4.1`, Apache-2.0, Windows wheel 약 85MB)로 넣는다. `serve` 그룹과 Docker 이미지에는 넣지 않는다. 설치: `uv sync --inexact --no-default-groups --group openvino --no-install-project`(이미 있는 다른 그룹을 지우지 않는다)
- 등록 전 점검(측정 아님): OpenVINO가 이 ONNX를 읽고 무작위 이미지 한 장(데이터셋 아님)에서 유한한 점수와 [1, 256, 256] 맵을 낸다. 컴파일된 설정은 스트림 1, 추론 스레드 6, 하이퍼스레딩 끔, f32였다. 명령 경로는 R0만 한 범주(pcb4, R0와 기록의 비교만)와 팔마다 1회 호출로 확인했고, 그 출력은 기록으로 쓰지 않는다

### (1) 점수 동일성 (언제든 잰다)
- dev 평가 세트 1,398장(겹 0 정상 1,158장 + dev 결함 240장, 280px 리사이즈 캐시)을 팔마다 한 장씩 채점한다. 한 이미지를 세 팔이 차례로 처리하고 점수와 맵(256×256)을 R0와 비교한다
- 먼저 R0가 6단계 기록(`dinomaly_serving score --protocol dev`, `outputs/dms-280-car-onnx-fp32-dev`)과 같은지 본다: 이미지 점수 최대 상대 차이 1e-6 이하(같은 파일, 같은 런타임이라 0을 기대한다). 어긋나면 환경이 바뀐 것이므로 어느 팔도 후보로 적지 않고 원인을 적는다
- 팔 Rk(R1, R2)는 R0에 대해 넷을 모두 만족하면 **통과**다: (가) 이미지 점수 최대 상대 차이 ≤ 1e-3, (나) 맵 최대 절대 차이 ≤ 1e-3, (다) dev 평균 이미지 AUROC(12개 범주 평균) 차이의 절댓값 ≤ 0.01%p, (라) 12개 범주 모두에서, 그 팔 자신의 겹 0 정상 점수로 다시 계산한 홀드아웃 임계값(목표 5%)이 R0의 같은 계산과 같은 겹 0 정상 이미지를 표시한다
- R2가 이 모델을 읽거나 컴파일하지 못하면 (1) 불통과로 적는다
- **브리프에서 바꾼 것 (측정 전)**: 브리프의 "홀드아웃 임계값이 같은 이미지를 표시"를 (라)처럼 각 팔 자신의 임계값으로 정했다. 아티팩트에 저장된 임계값은 R0로 채점한 바로 그 겹 0 정상 점수 가운데 하나(순위 l번째 값)다. 그 값을 다른 팔의 점수에 그대로 쓰면, 임계값 자리의 이미지 한 장이 마지막 비트 차이만으로 판정이 바뀔 수 있다(서비스 판정은 `점수 > 임계값`). 런타임을 바꾸면 임계값도 그 런타임의 점수로 다시 잡으므로(아래 결정) (라)가 실제 운영에 맞는 비교다. 저장된 임계값을 그대로 썼을 때 판정이 바뀌는 이미지 수(1,398장 중)와, 자기 임계값에서 dev 결함의 판정이 바뀌는 수는 판정 없이 적는다
- 리포트 `reports/runtime/parity.json`

### (2) 지연 (한가할 때)
- 한가함: 시작 전 1분 동안의 전체 CPU 사용률이 10% 미만이고, 같은 1분 동안 5초마다 읽은 GPU 사용률(`nvidia-smi`)의 평균이 10% 미만이면 시작한다. CPU 조건은 규칙 변경 6과 같고 GPU 조건을 더했다. 1분씩 최대 60분 기다리고, 그래도 한가하지 않으면 그대로 재고 조건을 수치 옆에 적는다. CPU 사용률은 Windows `GetSystemTimes`로 잰다
- 재는 것은 4·6단계와 같다: 범주 pcb1의 dev 풀 정상 앞 50장(280px 캐시)을 한 장씩, 워밍업 5회 뒤 50회(`ReconstructionInspector.run`: 정규화 + 모델 호출, 점수와 맵 반환). 1500×1000 사진을 280px로 줄이는 시간(PIL BICUBIC, 20회 중앙값)을 세션 시작 때 한 번 재서 모든 팔에 더한다
- 블록: 세 블록, 블록마다 세 팔을 한 번씩 돌리고 순서를 바꾼다(1: R0 R1 R2, 2: R1 R2 R0, 3: R2 R0 R1). 팔의 실행 하나는 새 프로세스에서 모델을 읽고 워밍업 뒤 50회를 잰다(앞 팔의 스레드 풀이 남아 끼어들지 않게). 실행마다 직전 5초 CPU 사용률과 GPU 사용률, 세션이 끝난 뒤 1분 동안의 CPU·GPU 사용률을 적는다
- 팔의 지연 = 리사이즈 + 세 블록 150회 추론의 중앙값. 블록별 중앙값과 p95도 적는다. **속도 이득 = 1 − (Rk 지연 / R0 지연)**
- 리포트 `reports/runtime/latency.json`

### H22와 결정
- **H22** 팔 Rk가 (1)을 통과하고, 같은 세션에서 속도 이득이 10% 이상이면 서빙 런타임 후보로 적는다(지지). 둘 중 하나라도 어긋나면 단순함을 위해 onnxruntime 기본 설정(R0)을 그대로 둔다(기각, 어느 조건인지 적는다). R1(스레드 12)은 런타임이 아니라 설정 대조라서, R1이 H22를 만족하면 onnxruntime 스레드 설정의 후보로 적는다
- 후보가 나와도 이 항목에서는 서비스 코드, 아티팩트, Docker 이미지를 바꾸지 않는다. 실제 교체는 더 큰 입력(예: 308px + CAR)을 열 때만 하고, 그때에 한해 판정 없는 ONNX 봉인 테스트 재채점 한 번(장부 한 줄)과 그 런타임의 겹 0 점수로 임계값 다시 잡기를 한다. 6단계 수치는 그대로 둔다

## 규칙 변경 기록
1. **2026-09-30, 봉인 테스트를 재기 전.** 리사이즈 캐시 생성을 봉인 규칙의 예외로 적었다. 처음 규칙은 "`--allow-test`를 준 실행에서만 읽는다"였는데, 캐시는 전체 이미지를 한 번에 배열로 옮겨야 해서 글자 그대로는 지킬 수 없었다. 캐시 생성은 점수를 내지 않고, 만들 때마다 장부에 남긴다. 256px 캐시는 이 기록 장치가 생기기 전(같은 날 16:37)에 만들었으므로 장부 첫 줄에 손으로 적었다
2. **2026-09-30, 봉인 테스트를 재기 전.** "보정 표본 수 n에 따른 실제 오검출률"의 비교 기준을 Beta 분포의 분위에서 같은 표본 크기의 모의로 바꿨다. 코드 리뷰에서 나온 지적이다: 관측값은 크기가 정해진 풀에서 비복원으로 뽑은 부분표본과 고정된 테스트 집합에서 나오므로, 점수가 완전히 교환 가능해도 관측 폭이 Beta 폭보다 좁고(균등 난수 실험에서 풀 300·n 200일 때 절반) 범주별 평균에는 그 풀과 테스트 집합 고유의 오차가 실린다. Beta 분위와 그대로 비교하면 흔들림과 치우침을 가를 수 없다. 이 항목은 판정이 없는 참고 자료이고 H1~H4의 판정 규칙은 바꾸지 않았다
3. **2026-09-30, 3단계를 재기 전.** 3단계의 큰 틀에 적었던 "새 조명의 정상 32장으로 다시 맞춘다"를 30장으로 고쳤다. M2AD는 범주마다 학습 시편이 30개라, 시점 하나를 맡는 검사기가 새 조명에서 쓸 수 있는 정상 이미지는 30장이 전부다. 가설 번호는 H9, H11, H12를 쓴다(H10은 쓰지 않았다)
4. **2026-09-30, 2단계를 재기 전.** 지도 학습 헤드의 규칙 두 가지를 코드 리뷰 뒤에 고쳤다. (가) 검증 AUROC가 같을 때 "앞선 에폭"을 쓰던 것을 "뒤의 에폭"으로 바꿨다. 쉬운 범주에서는 검증 AUROC가 5에폭 만에 1.0에 닿아 그 뒤가 전부 동점이 되는데, 앞선 에폭을 고르면 손실이 아직 절반쯤인 덜 학습된 헤드가 뽑혀 지도 학습 쪽이 불리해진다. (나) 점수 맵을 sigmoid 확률 대신 로짓으로 저장한다. 확률을 float16으로 저장하면 로짓이 8.3을 넘는 픽셀이 모두 1.0이 되어 픽셀 지표에 동점이 생긴다. 로짓과 확률은 순서가 같으므로 순위 기반 지표(AUPRO, 픽셀 AUROC)의 정의는 달라지지 않는다
5. **2026-09-30, 4단계를 재기 전.** 코드 리뷰에서 DINOv2 내보내기는 INT8로 양자화할 수 없다는 것이 확인됐다. onnxruntime 1.30의 정적 양자화 전처리가 클래스·레지스터 토큰의 Expand 노드에서 실패하고, 그 단계를 건너뛰고 양자화하면 특징이 FP32와 거의 무관해진다(사전학습 가중치 252px에서 상관 0.07). 그래서 DINOv2 설정이 서빙 구성으로 뽑히는 경우의 처리(FP32만 채점, H14는 판정하지 않음)를 4단계 규칙에 더했다. 같은 리뷰에서 지연 표가 리사이즈 시간을 빼고 있던 것도 고쳤다(규칙은 처음부터 "리사이즈 + 추론"이었고 코드가 어긋나 있었다)

6. **2026-10-01, 4단계 서빙 구성을 고르기 전(4단계 test 측정 전).** 지연을 처음 잰 10:08~10:24에 이 PC에서 다른 프로그램(게임, 움직이는 배경화면)이 돌고 있었다. 측정 직후 전체 CPU 사용률이 32~38%였다. 규칙은 측정 장비만 정했고 다른 부하가 없어야 한다는 조건을 적지 않았다. 그 결과에서 CPU 지연이 예산 200ms 바로 위인 구성(wrn50-256-r0.01, 216.8ms)이 있어, 부하 때문에 선택이 바뀔 수 있다. 그래서 **서빙 구성 선택에 쓰는 지연은 측정 시작 직전 1분 동안 전체 CPU 사용률 평균이 10% 미만일 때 다시 잰 값으로 한다.** 처음 잰 값은 `reports/stage4/latency-loaded.json`으로 남기고 결과 표에 같이 싣는다. 이 결정은 dev 격자 결과와 처음 지연 값을 본 뒤에 내렸다. 그래서 선택 규칙(CPU 리사이즈+추론 200ms 이하 가운데 dev 평균 이미지 AUROC 최고, 같으면 뱅크가 작은 쪽)과 스레드 설정(onnxruntime 기본값)은 바꾸지 않고, 다시 잰 값으로 고른 구성을 그대로 쓴다. 두 측정에서 고른 구성이 다르면 그 사실을 적는다. 부하 상태의 선택은 dinov2_vits14-252-r0.01(117.5ms, dev AUROC 91.34)이었다
