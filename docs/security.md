# 보안 점검 기록

검사 서비스(`src/defect_inspect/service.py`)를 동적 스캔(DAST)으로 점검한 기록이다. 스캔은 이 PC에서 띄운 로컬 서비스(`127.0.0.1:8093`)에만 한다.
서비스 이미지에 들어가는 의존성을 공개 취약점 데이터베이스와 대조한 기록은 DAST와 따로 맨 아래 [의존성 취약점 대조](#의존성-취약점-대조) 절에 적는다(2026-10-24부터).
compose 기본 설정으로 띄운 컨테이너의 자원 한도(업로드 임시 저장소, 메모리)를 실제로 채워 확인한 기록은 그 앞의 [운영 확인](#운영-확인) 절에 적는다(2026-11-05부터).
업로드 디코딩이 파일 크기·화소 수 한도 안에서도 구조 항목 때문에 쓰는 자원을 재고, 알려진 증폭 경로를 디코딩 전의 구조 사전 검사로 막은 기록은 [업로드 구조 점검](#업로드-구조-점검) 절에 적는다(2026-11-24부터).

## 설정
| 도구 | 설정 파일 | 비고 |
|---|---|---|
| HawkScan (StackHawk) | `stackhawk.yml` | 체험 기간이 2026-10-05에 끝난다 |
| OWASP ZAP 2.17.0 | `zap/automation.yaml`, `zap/run_zap.sh` | Apache-2.0. 공식 크로스플랫폼 패키지를 Java 21로 직접 실행(Docker 없음) |

두 설정은 같은 일을 한다.
- 서비스의 OpenAPI 명세(`/openapi.json`)에서 경로를 가져온다
- OpenAPI로는 이미지 업로드를 만들 수 없어 모든 POST가 폼 검증(422)에서 멈추므로, 실제 multipart 요청을 HAR 시드로 넣는다(`hawk/make_seed_har.py`). 합성 범주 `demo`로 도는 오프라인 서비스는 `hawk/seed.har`, 아티팩트로 띄운 서비스는 그 범주로 만든 시드(예: `hawk/seed-pcb1.har`)를 쓴다
- spider, passive scan, 기본 정책 active scan
- 모든 요청에 일회용 관리자 토큰(`X-Admin-Token`)을 붙여 `POST /calibrate`와 `DELETE /calibrate`까지 닿게 한다. 토큰은 실행할 때 환경 변수로 주고 파일에 적지 않는다

HawkScan은 ZAP 엔진 위에 만든 상용 도구지만 규칙 목록, 기본 설정, 버전이 ZAP 배포판과 같지 않다. 그래서 **두 도구의 결과는 일대일로 비교하지 않고, 같은 도구의 기록끼리만 비교한다.**

실행 (Git Bash, 스캐너 출력은 파일로만 보낸다):
```bash
ADMIN_TOKEN=$(python -c "import secrets; print(secrets.token_urlsafe(24))")
# 오프라인 서비스 (모델 파일 없음, 범주 demo)
DEFECT_INSPECT_ADMIN_TOKEN=$ADMIN_TOKEN uv run uvicorn defect_inspect.service:create_offline_app --factory --port 8093
# 아티팩트로 띄운 서비스라면 DEFECT_INSPECT_ARTIFACTS=<아티팩트 폴더> ... service:create_app 이고, 시드는 그 범주의 것

# HawkScan (아티팩트 서비스는 SEED_HAR=hawk/seed-pcb1.har 를 더한다)
APP_ID=<application id> ADMIN_TOKEN=$ADMIN_TOKEN hawk scan --hawk-mem=4g stackhawk.yml > work/hawk.log 2>&1
# OWASP ZAP (ZAP_DIR: zap-2.17.0.jar 가 있는 폴더. 결과는 work/zap/<이름>/)
ZAP_DIR=<폴더> ADMIN_TOKEN=$ADMIN_TOKEN zap/run_zap.sh <이름> [시드 HAR]
```

## 기록

### 2026-10-01 HawkScan (서비스 모델 PatchCore, 오프라인 서비스)
- 1회차(scan `aa03b755`): OpenAPI만으로 스캔했다. `POST /inspect` 399회와 `POST /calibrate` 604회가 모두 폼 검증(422)에서 멈춰 처리 코드에 닿지 않았다. 그래서 HAR 시드를 만들었다
- 2회차(scan `b821d222`, HAR 시드 추가): 지적은 Anti-CSRF Tokens Check(Medium) 1건이다. 데모 페이지(`GET /`)의 폼에 anti-CSRF 토큰이 없다는 것이다. 오탐으로 표시했다. 폼은 `fetch()`로만 보내고, 서비스는 쿠키를 쓰지 않는다. 쓰기 경로(`/calibrate`)는 다른 출처의 페이지가 붙일 수 없는 `X-Admin-Token` 헤더가 필요하고(CORS 없음), 다른 출처의 쓰기 요청은 Sec-Fetch-Site/Origin으로 거절한다(`tests/test_service.py`)

### 2026-10-04 서비스 모델 교체 전후 (규칙, 스캔 전에 커밋)
2026-10-04 사용자가 서비스 모델을 6단계의 dms-280-car로 바꾸기로 정했다. 교체는 `service.py`가 복원 방식(Dinomaly) 아티팩트도 읽게 하는 것이다. 바뀌는 것은 범주마다 읽는 아티팩트(메모리 뱅크 → 모델이 직접 점수를 냄), `/categories`의 응답 필드, `/calibrate`가 점수를 내는 방법이다. 경로와 보호 장치(Host 검사, 다른 출처의 쓰기 요청 거절, 관리자 토큰, 본문 크기 제한, 보안 헤더)는 바꾸지 않는다. HawkScan 체험이 끝나는 시점이라 두 도구로 교체 전후를 스캔한다.

- 대상 (1) 교체 전: 이 규칙 커밋의 오프라인 서비스(합성 PatchCore 범주 `demo`, 시드 `hawk/seed.har`). 서비스 코드는 2026-10-01 스캔 때와 같다
- 대상 (2) 교체 후: 교체 커밋의 서비스를 `artifacts/dms-280-car`(12개 범주, onnxruntime CPU FP32)로 띄운 것, 시드 `hawk/seed-pcb1.har`
- 같은 날 (1) → 교체 커밋 → (2) 순서로, 대상마다 HawkScan과 ZAP을 한 번씩 돌린다. 둘 다 `127.0.0.1:8093`, 대상마다 새 일회용 토큰
- **통과 조건**: 도구마다 (2)에 (1)에 없던 High 또는 Medium 경보(규칙 이름 기준)가 없다. 새로 나온 것은 고치거나, 고치지 않는 사유를 이 문서와 README에 적는다. Low와 Informational은 적기만 한다
- ZAP (1)에서 HawkScan이 오탐으로 표시한 Anti-CSRF(Medium)가 다시 나오는지 적는다(판정 없음)
- ZAP active scan은 120분에서 끊는다. 끊기면 그 사실을 적는다
- 결과 요약은 `reports/dast/`에 JSON으로 남긴다(경보 이름, 위험도, 신뢰도, 건수, 경로. 토큰과 요청 본문은 넣지 않는다)
- 2026-10-05 이후 다시 스캔할 때는 ZAP을 쓰고, 이 날의 ZAP 기록과 비교한다

### 2026-10-04 결과 (도구가 바뀌었다: HawkScan → OWASP ZAP. 두 도구의 결과는 직접 비교하지 않는다)

| 도구 | 대상 | High | Medium | Low | Informational | 스캔 중 요청 (처리 코드에 닿은 업로드) |

- **판정: 통과.** 두 도구 모두 (2)에 (1)에 없던 High·Medium이 없다. 경보의 종류와 건수가 교체 전후에 같고, 네 스캔 모두 서비스가 5xx를 한 번도 내지 않았다(모델이 실제로 도는 (2)에서도 대기열이 넘친 503이 없었다)
- HawkScan의 Medium은 2026-10-01에 오탐으로 표시한 그 지적(데모 페이지 폼의 anti-CSRF 토큰)이고, 두 스캔 모두 오탐 상태로 남아 있다. 사유는 위 2026-10-01 기록과 같다
- **ZAP은 이 Anti-CSRF Medium을 다시 내지 않았다.** HawkScan의 "Anti-CSRF Tokens Check"와 같은 이름의 active 규칙은 ZAP 공식 배포판에 든 규칙 묶음(`ascanrules` release)에 없고, ZAP의 패시브 규칙 "Absence of Anti-CSRF Tokens"(10202)는 이 폼에 경보를 내지 않았다. 같은 폼을 보고 도구에 따라 결과가 다르다는 것이 "직접 비교하지 않는다"의 한 예다
- ZAP의 Informational 두 건은 데모 페이지가 링크 없이 스크립트로 그려지는 페이지라는 표시(Modern Web Application, 10109)와, User-Agent를 바꿔 보낸 `/calibrate` 요청의 응답이 원래 응답과 달랐다는 기록(User Agent Fuzzer, 10104)이다. `/calibrate`는 부를 때마다 임계값 상태가 바뀌어 응답 본문(`previous_threshold` 등)이 달라지는 경로라서, User-Agent에 따라 처리가 갈리는 것이 아니다. 둘 다 고칠 것이 아니다
- ZAP의 한계: DOM XSS 규칙은 이 PC에 Firefox가 없어 브라우저를 띄우지 못하고 건너뛰었고(두 대상 모두), Parameter Tamper 규칙은 multipart 매개변수를 바꾸다 ZAP 내부 오류(NullPointerException)로 16번 멈췄다(두 대상 모두). 그 밖의 기본 정책 규칙은 돌았다
- **2026-10-04 정정 (검토 지적)**: 바로 위 "그 밖의 기본 정책 규칙은 돌았다"는 틀렸다. ZAP 로그에 규칙마다 남는 완료·건너뜀 줄을 다시 세면, 두 대상 모두 active 규칙 53개 가운데 3개가 돌지 않았다. DOM XSS(위 사유), **Log4Shell**(CVE-2021-44228·45046. 응답이 아니라 외부 콜백으로 확인하는 규칙이라 OAST 콜백 서비스가 필요한데, 설정하지 않아 건너뛰었다), 스크립트 규칙(켠 스크립트가 없어 해당 없음)이다. 나머지 50개는 완료로 기록됐고, 그중 9개(XXE, 지수 엔터티 확장, SOAP 두 개, Padding Oracle, HTTP Only Site, HTTPS as HTTP, GET for POST, Persistent XSS)는 대상에 맞는 요청이 없어 한 건도 보내지 않았다. 서비스는 Python이라 Log4j를 쓰지 않지만, 이 스캔이 Log4Shell을 확인한 것은 아니다. 판정(교체 뒤 새 High·Medium 없음)은 바뀌지 않는다. 다음 ZAP 스캔을 이 기록과 비교할 때 이 세 규칙은 돌지 않은 것으로 본다
- 스캔 시간: HawkScan (1) 약 30초, (2) 약 3분. ZAP (1) 약 1분(active scan 28초), (2) 약 18분(active scan 17분 30초, 120분 한도 안). (2)는 업로드마다 모델이 CPU에서 돌아서 길다

### 2026-10-15 결과 (OWASP ZAP 2.17.0, 서비스 코드 `b17ce35`)
규칙 커밋(`b17ce35`, 위 절) 뒤에 (1) 오프라인 서비스 19:08~19:10, (2) dms-280-car 서비스 19:12~20:07 순서로 돌렸다. 대상마다 새 일회용 토큰, 둘 다 `127.0.0.1:8093`. 요약 `reports/dast/2026-10-15.json`. 그동안 다른 프로젝트 작업들이 CPU를 거의 100% 쓰고 있어 (2)의 active scan이 52분 58초 걸렸다(2026-10-04는 17분 30초, 120분 한도 안).

| 대상 | High | Medium | Low | Informational | 스캔 중 요청 (처리 코드에 닿은 업로드) | 5xx |
|---|---|---|---|---|---|---|
| (1) 오프라인 | 0 | 0 | 0 | 3 (Modern Web Application, User Agent Fuzzer, **Information Disclosure - Suspicious Comments**) | 6,895 (`POST /inspect` 200 517회, `POST /calibrate` 200 1,320회) | 0 |
| (2) dms-280-car | **1 (SQL Injection - SQLite (Time Based))** | 0 | 0 | 3 (같은 셋) | 6,890 (516회, 1,323회) | 0 |

- active 규칙: 두 대상 모두 53개 시작, 50개 완료, 3개 건너뜀(DOM XSS, Log4Shell, 스크립트 규칙. 2026-10-04와 같은 사유), 완료 중 9개는 보낸 요청 0건, Parameter Tamper의 ZAP 내부 NullPointerException 16회. 2026-10-04와 같다

## 운영 확인

DAST와 의존성 대조 밖에서, compose 기본 설정으로 띄운 컨테이너가 자원 한도 안에서 도는지 실제로 채워 본 기록이다. 서비스 코드와 설정은 바꾸지 않고 확인만 한다.

### 2026-11-05 업로드 임시 저장소를 가장 많이 채웠을 때의 컨테이너 메모리 (규칙, 확인 전에 커밋)

## 업로드 구조 점검

DAST·의존성 대조와 따로, 업로드 디코딩이 파일 크기·화소 수 한도 안에서도 작업 스레드와 메모리를 얼마나 쓸 수 있는지 재 보고, 알려진 증폭 경로를 디코딩 전의 구조 사전 검사로 막은 기록이다.

### 2026-11-24 업로드 구조 사전 검사
- **문제**: 비인증 `POST /inspect`와 관리자 `POST /calibrate`는 받은 바이트를 `service._decode`에서 `Image.open`에 넘긴다. 서비스는 파일 20MiB와 화소 2,500만으로 압축 폭탄을 막는다고 보았고, 코드 주석도 "Image.open은 헤더만 읽으므로" 화소 수 검사를 디코딩 전에 하면 충분하다고 적었다. Pillow 13.0.0에서는 그렇지 않다. Pillow와 그 밑의 libjpeg-turbo(3.2.0)·libtiff(4.7.2)는 화소 수와 무관한 구조 항목마다 일을 한다(폭 1 × 높이 N인 그림은 N화소라 화소 수 검사를 통과한다)
  - TIFF: 무압축이면 `StripOffsets`(타일이면 `TileOffsets`) 원소마다 `_Tile` 하나(약 300바이트, 8.6μs)를 만들고 디코딩 때 조각마다 디코더를 만든다. 표를 BYTE형으로 적으면 Pillow는 값을 `bytes` 하나로 두었다가 바이트마다 돈다(원소가 1바이트라 LONG 표보다 4배 촘촘하다). 디코딩이 끝나면(쪽이 하나일 때) `getexif()`로 Exif·GPS·Interop 하위 IFD를 무리마다 따로 열어 모든 항목을 파이썬 수의 튜플로 푼다. RATIONAL은 원소마다 `IFDRational`(약 150바이트, 3.7μs)이다. 가리킴 값이 여럿이면 첫 값을 따라가고, Interop 가리킴은 첫 IFD가 아니라 Exif IFD 안의 것을 따라간다. 하위 IFD의 비용은 `Image.open`이 아니라 디코딩 단계에서 생긴다
  - JPEG: 첫 SOS 앞의 마커마다 바이트열과 튜플을 쌓고(약 130바이트, 1.5μs), Exif 조각은 이어 붙일 때마다 지금까지의 Exif 전체를 복사한다. 세그먼트 안을 파이썬으로 훑는 Photoshop 자원(APP13)은 바이트당 약 0.1μs, 마커 사이의 쓰레기 바이트는 한 바이트씩 파이썬 반복으로 건너뛴다(바이트당 약 0.1μs). 점진 JPEG은 스캔(SOS)마다 libjpeg가 그림 전체의 MCU를 돈다(자료가 모자라면 0으로 채운다). 스캔 수 문제는 이 사전 검사를 넣기 전부터 있던 것이다
  - PNG: 알 수 없는 사설 청크마다 `private_chunks`에 쌓고(약 120바이트, 4μs), 이미지 데이터(IDAT) 조각마다 파이썬 반복을 한 번 돈다(3.4μs). 압축을 푸는 청크(iCCP·zTXt·iTXt)는 청크마다 1MiB까지 풀며, Pillow의 텍스트 메모리 합계(64MiB)는 iCCP와 키가 빈 zTXt, UTF-8이 아닌 iTXt에 걸리지 않는다. 청크는 첫 IDAT 앞뒤로 IEND까지 읽는다
  - BMP: RLE(압축 1·2)는 Pillow의 파이썬 디코더가 명령 두 바이트마다 한 바퀴를 돌고, 화소를 늘리지 않는 명령(줄 끝, 이동 0)은 파일 끝까지 돈다. RLE4는 화소마다 파이썬 반복을 돈다

- **조치** (`src/defect_inspect/image_precheck.py`, `service._decode`가 `Image.open` 전에 부른다): 바이트열을 직접 훑어 알려진 증폭 경로의 구조 항목을 세고, 형식별 상한을 넘으면 기존의 '읽을 수 없는 이미지'와 같은 400(`the upload is not a readable image`)을 낸다. 거절만 하고 바이트열을 바꾸지 않으므로 통과한 파일의 디코딩 결과는 그대로다. 경로마다 Pillow 13.0.0과 libjpeg-turbo·libtiff가 읽는 규칙을 따라가고(근거가 된 소스 위치는 모듈의 주석에 있고, 그 전제가 설치된 Pillow에서도 참인지 보는 시험이 있다), 어느 쪽을 읽을지 가를 수 없는 곳은 더 넓게 센다. 읽을 수 없는 구조(잘림, 범위 밖 오프셋)에서는 멈추고 통과시켜 Pillow가 판단하게 한다. 모든 반복에 상한이 있어서 파일이 아무리 커도 검사 비용은 상한에 묶인다(고친 코드로 잰 검사 자체의 비용: 20MiB JPEG의 첫 스캔 뒤가 무작위 자료면 17ms, 모두 0xFF로 만든 최악이면 0.2초, PNG 청크 상한 끝 88ms, TIFF IFD 16개 × 항목 1,024개 4ms. 입력을 복사하지 않아 파이썬 메모리는 20KiB 안쪽이다). WebP는 이 검사를 거치지 않는다(아래 한계)
  - `TiffImagePlugin.READ_LIBTIFF = True`로 무압축 TIFF도 libtiff 한 덩어리로 읽으면 스트립 표 문제는 없어지지만 쓰지 않았다. YCbCr TIFF의 디코딩 결과가 달라진다(libtiff 쪽은 RGB 모드로 읽는다. RGB·L·1·P·CMYK·LAB·여러 스트립 파일은 같고 YCbCr만 다른 것을 실행으로 확인했다). 또 Exif 하위 IFD 쪽 비용은 그대로다(RATIONAL 20만 개를 열어 RGB로 바꿀 때 파이썬 메모리 30MiB, 설정을 켜도 29MiB)
  - TIFF: 숫자 형식(SHORT·LONG·RATIONAL 등) 값은 모두 센다. BYTE형 값은 Pillow·libtiff가 원소마다 도는 첫 IFD 태그만 센다: `StripOffsets`·`TileOffsets`(바이트마다 타일을 만든다), `StripByteCounts`·`TileByteCounts`(압축 TIFF에서 libtiff가 원소마다 8바이트 정수로 바꾼다), `ColorMap`(원소마다 팔레트 값을 만든다), `SampleFormat`·`ExtraSamples`(원소마다 `max`·`min`을 돈다). 설치된 Pillow 소스에서 BYTE 값을 원소마다 도는 곳을 모두 찾았고, 실행으로 비용이 원소 수를 따라가는지 확인했다(태그마다 BYTE형 10만·40만 개로 열어 보았고, C 수준으로 도는 `SampleFormat`은 2,000만 개에서 0.30초, libtiff 경로의 표는 200만 개에서 +17\~32MiB). XMP·Photoshop 자원처럼 정상 파일에서도 큰 BYTE 값은 Pillow가 돌지 않으므로 세지 않는다. 가리킴은 센 모든 IFD에서 Exif·GPS·Interop 태그를 모아 값의 개수와 무관하게 첫 값을 따라간다. 같은 태그가 여럿이면 정수로 읽히는 것을 모두 따라간다(Pillow는 처음으로 쓸 수 있는 항목을 쓰는데, 형식이 지원되지 않거나 태그 자료 예산을 넘은 앞 항목을 버리므로 처음 것만 따라가면 미끼를 앞에 둘 수 있다). (가리킴 태그, 위치) 쌍마다 한 번씩 센다(Pillow가 무리마다 따로 열어, 세 가리킴이 한 IFD를 가리키면 그 IFD를 세 번 푼다). 가리킴이 첫 IFD 자신이면 그 IFD를 하위 IFD로서 다시 세어 표도 숫자 합계에 넣는다. 따라간 IFD가 16개를 넘으면 멈추지 않고 거절한다(멈추면 미끼 가리킴으로 한도를 채울 수 있다). 다음 쪽(여러 쪽 TIFF의 둘째 쪽 이후)은 Pillow가 열 때 오프셋만 기억하고 따라가지 않으므로 세지 않는다(IFD 10만 개짜리 사슬을 열어 RGB로 바꿔도 CPU 0.00초였다). BigTIFF(`II+\0`)는 Pillow가 열기 때문에 같은 검사를 한다
  - JPEG: 첫 SOS까지는 Pillow의 `_open`과 같은 규칙으로 세고, 그 뒤의 스캔(SOS) 수는 libjpeg가 마커를 알아보는 규칙으로 센다. 엔트로피 자료 안의 0xFF는 늘 0x00을 덧붙여 적으므로(byte stuffing) 'FF 다음이 00·FF가 아닌 바이트'만 마커로 보아 자료 안의 바이트를 스캔으로 잘못 세지 않는다. 길이 칸이 있는 세그먼트는 길이만큼 건너뛰고, EOI에서 멈춘다(EOI 뒤에 붙은 자료는 libjpeg가 읽지 않으므로 세지 않는다. 동영상이 붙은 사진 같은 파일을 막지 않는다). 첫 SOS 뒤의 세그먼트 수도 1,000개로 묶는다. libtiff도 TIFF 안의 JPEG에는 같은 기본 상한(스캔 100개)을 둔다(실행해 보면 'Scan number 100 exceeds maximum scans (100)'으로 멈춘다)
  - PNG: 압축을 푸는 청크(iCCP·zTXt·iTXt)를 위치와 종류에 상관없이 합쳐 센다
  - BMP: 정보 머리가 BITMAPINFOHEADER 꼴(40·52·56·64·108·124바이트)이고 압축 칸이 RLE(1·2)일 때만 파일 크기를 본다. 무압축·비트필드 BMP는 C 디코더라 화소 수에 비례하므로 보지 않는다

- **상한 안에서 가장 비싼 입력** (고친 코드로 다시 잼. 이 PC, `service._decode(data, 64)`. 입력을 파일로 저장해 두고 새 프로세스마다 하나씩 쟀다. 메모리는 작업 집합 최고값의 증가다):

  잰 입력 가운데 형식마다 가장 비싼 것은 BMP 3.45초, PNG 2.56초, TIFF 약 1.8초(어림), JPEG 1.66초다. 표의 값은 입력 몇 개를 잰 것이고 더 비싼 입력이 없다는 뜻이 아니다: 표의 마지막 세 줄은 고친 코드의 독립 검토가 같은 상한 안에서 더 비싼 입력을 찾아 더한 것이다(같은 PC, 다른 작업이 함께 돌던 때). JPEG·BMP는 화소 수 한도(2,500만) 끝의 그림 자체를 푸는 비용(0.61초, 2.02초)이 큰 몫이다. PNG의 2.56초는 zlib가 작은 블록 열을 푸는 바이트당 비용(약 0.15초/MiB)이라 IDAT에 넣어도 같은 비율이고, 파일 크기 한도(20MiB)에서는 약 3초가 된다(어림). 구조 항목 수가 아니라 파일 크기에 비례하는 디코더 자체의 비용이라 이 검사로는 묶을 수 없다. 첫 판의 문서가 적은 '상한 안에서 가장 비싼 입력은 1.3초'는 틀렸다
- **고친 뒤 재현**: 위 표의 크기 그대로 입력 가운데 첫 판이 막은 다섯(TIFF 260만 개·`StripByteCounts` 없는 520만 개·80만 개, JPEG 마커 520만 개, PNG 사설 청크 170만 개)을 고친 코드에 다시 넣으면 모두 400(`the upload is not a readable image`)이고 CPU 0.00초, 작업 집합 증가 3MiB 이하다. 스트립 80만 개 TIFF를 오프라인 앱의 `POST /inspect`에 보내면 400이 0.0초에 돌아온다(고치기 전 200, 8.2초). 독립 검토의 재현 스크립트를 줄인 크기로 다시 돌리면 TIFF 하위 IFD(개수 1, Exif IFD 안의 Interop, 개수 2, 개수 2와 가짜 중복, GPS 개수 2. RATIONAL 30만 개), 가리킴 형식 조합(정수 형식 여섯 × 개수 1·2, RATIONAL 20만 개), BYTE형 스트립·타일 표와 ColorMap 20만 개, PNG IDAT 뒤 iCCP 1,000개·키가 빈 zTXt 1,000개·IDAT 앞 iCCP 900개, RLE8 BMP 4.8MiB, 5000×5000 점진 JPEG + 스캔 2,000개가 모두 사전 검사에서 거절되고 `_decode`는 CPU 0.00초에 400이다. Pillow가 따라가지 않는 가리킴(RATIONAL·SRATIONAL·FLOAT·DOUBLE)과 ASCII·UNDEFINED로 적은 표는 통과하고 Pillow도 돌지 않는다(0.00초). 상한 안인 RLE8 1.9MiB(0.38초)와 스캔 100개인 5000×5000 점진 JPEG(0.38초)은 통과한다. 검토가 찾은 다섯 갈래의 크기 그대로 입력(BYTE형 `StripOffsets` 2,000만 개, 값이 둘인 Exif 가리킴·Exif IFD 안의 Interop 가리킴 뒤 RATIONAL 260만 개, IDAT 뒤 iCCP·키가 빈 zTXt 9,999개, 5000×5000 점진 JPEG + 스캔 130만 개, RLE8 19.8MiB)은 회귀 시험에서 사전 검사가 거절한다(디코딩까지는 돌리지 않았다)
- **차분 확인**: 검사 판정과 Pillow가 실제로 한 일을 견주는 무작위 시험이다. TIFF는 검토가 만든 차분 퍼저(검사 상한을 항목 64·스트립 500·숫자 1,000으로 줄이고 Pillow가 푼 값 원소 수·만든 타일 수를 잰다)를 시드 14개 × 12,000개 돌려 '통과인데 Pillow가 많이 푼' 입력이 0건이었다(첫 판에서는 시드마다 BYTE형 표와 중첩 Interop이 나왔다). 가리킴 개수 1\~3·중복·중첩·자기 자신과 순환, 원소마다 도는 BYTE형 태그를 섞은 TIFF 약 20만 개(IFD 상한도 6으로 줄임)에서도 0건이었고, 통과한 입력에서 Pillow가 푼 원소는 최대 997개로 줄인 숫자 상한(1,000) 안이었다. JPEG·PNG·BMP는 정상 파일에 구조(머리 세그먼트, Exif·MPF·Photoshop 자원, 첫 스캔 뒤의 스캔·DHT·RST·쓰레기·EOI·뒤에 붙은 자료, 사설·텍스트·압축 청크, RLE 명령 등)를 무작위로 더하고 상한을 줄인 검사를 통과한 것의 `_decode` CPU를 쟀다(형식당 150초, JPEG 26,255개·PNG 19,049개·BMP 58,449개). 통과한 것 가운데 가장 비싼 것은 JPEG 0.08초, PNG 0.05초, BMP 0.09초로 바탕 그림을 푸는 비용이었고 새 유형은 나오지 않았다
- **통과한 파일은 그대로**: 1,092개 입력에서 `_decode`(크기 280과 64, 작은 파일은 리사이즈 없이도)의 결과를 고치기 전(HEAD)의 코드와 고친 뒤의 코드로 2,897번 견주었고 모드·크기·화소 해시(또는 400의 문구)가 모두 같았다. 입력은 위 실제 파일 23개, 그것을 Pillow·OpenCV·tifffile로 여러 설정(PNG 압축 수준·팔레트, JPEG 품질·점진·서브샘플링·CMYK, TIFF 무압축·LZW·Deflate·PackBits·JPEG·Group 4·CMYK·YCbCr·LAB, 줄무늬 1·4·8줄, 타일 16·32·64, 평면 분리, 예측기, 큰 쪽 바이트 순서, BigTIFF, BMP, WebP)으로 다시 저장한 것, 시험 모음의 정상 입력이다. 시험 모음에 더한 정상 입력 7개(압축 청크 21개를 가진 PNG, 스캔 18·6개인 점진 JPEG, EOI 뒤에 FF DA가 300개 붙은 JPEG, 팔레트 TIFF, RLE8·RLE4 BMP)를 넣은 1,099개·2,918번도 모두 같았다. 고치기 전 결과는 정상 디코딩 1,021개(더한 7개를 넣으면 1,028개), 400이 71개(투명도 24, 읽을 수 없음 24, 16비트 22, 화소 수 1)였다. 봉인 테스트 이미지(`data/`)는 읽지 않았다
- **알려진 한계·받아들인 것**:
  - 이 검사가 막는 것은 알려진 증폭 경로뿐이다. 요청 하나가 쓰는 CPU 시간과 메모리를 직접 묶는 장치는 없고, 이 구조 상한이 그것을 대신하지 않는다. 구조 상한은 경로마다 따로 막는 방식이라 같은 종류의 변형이 더 나올 수 있다(첫 판은 한 번의 검토에서 다섯 갈래가 나왔다). **남은 과제**: 디코딩을 작업 프로세스로 분리해 요청마다 시간·메모리 한도에서 끝내는 것. 이번에는 하지 않았다
  - 상한 안에서도 비용은 0이 아니다(위 표, 잰 것 가운데 가장 비싼 것은 BMP 3.45초·PNG 2.56초). 작업자 둘이 동시에 이런 입력을 받으면 그만큼 다른 요청이 기다린다. 그중 BMP RLE4가 화소마다 도는 파이썬 반복(5000×5000에서 2.02초)과 JPEG 머리 안의 Exif RATIONAL 배열(0.69초)은 이번 상한으로 막지 않은 기존 비용이다. TIFF의 칸 밖 태그 자료(UNDEFINED 등)는 Pillow가 IFD를 읽을 때마다 복사해 메모리가 그 크기의 약 5배가 된다(2.9MiB에서 +14MiB. 선형이면 19MiB에서 약 95MiB이고 CPU는 0.02초). 구조 항목 수가 아니라 파일 크기에 비례하는 비용이라 세지 않는다
  - 상한을 넘는 정상 파일은 거절된다: 첫 SOS까지 2MiB를 넘는 JPEG(예: 2MiB가 넘는 ICC 프로파일), 스캔이 100개를 넘는 점진 JPEG, 프레임이 1만 개를 넘는 APNG, 압축 청크가 64개를 넘는 PNG, 스트립·타일 표가 10만 개를 넘는 TIFF(가늘고 긴 그림을 16×16 타일로 저장한 것 등), 4MiB를 넘는 RLE BMP(256색 사진을 RLE8로 저장하면 약 500만 화소부터). 점검한 정상 파일에는 없었다
  - 하위 IFD(Exif·GPS·Interop) 가리킴이 깨진 TIFF는 Pillow가 경고만 내고 받아 주지만, 가리킨 곳이 항목 1,024개를 넘는 표로 읽히면 이 검사가 거절한다. 이 판은 가리킴을 더 넓게 따라가므로(값이 여럿인 것, 하위 IFD 안의 것, 같은 태그의 모든 항목) 그런 거절이 생길 자리도 늘었다. 가리킴을 믿지 않으면 큰 표를 하위 IFD에 숨길 수 있어 가르지 않았다
  - WebP는 사전 검사를 하지 않는다. 5000 × 5000 무손실 WebP(1KB)는 0.25초·+382MiB(같은 크기 PNG·JPEG의 4배 남짓, 작업자 둘이면 약 0.75GiB로 한도 안)다. 헤더를 극단값으로 만든 입력 11건(BMP 팔레트 수 최댓값·데이터 없는 5000×5000 24비트·RLE8 5000×5000, PNG 머리만 5000×5000·21억 × 21억, JPEG SOF 65535 × 65535, 16비트 TIFF 4000×4000 등)은 첫 판으로 잰 대로 400이거나 화소 수 한도 안의 비용이었다. 이 판의 규칙은 그 입력들의 판정을 바꾸지 않아 다시 재지 않았다
  - 확인하지 못한 것: Linux 휠의 수치(파이썬 객체 크기는 같다), 컨테이너 `mem_limit: 2g`에서의 실제 종료, 실제 카메라·스캐너·산업용 카메라 파일(라이브러리가 저장한 파일과 합성 파일로만 확인했다), libjpeg 기본 순서가 아닌 인코더(mozjpeg 등)의 스캔 수, TIFF 안의 옛 JPEG(OJPEG) 경로. 20MiB 크기 그대로의 최악 입력 가운데 BYTE형 표(약 130초·4.4GiB)와 스캔(약 30분)은 이 PC가 버티지 못해 줄인 크기에서 재고 선형으로 외삽했다
  - 서비스 코드를 바꿨으므로 다음 DAST 재스캔의 범위에 든다
- **회귀 시험** (`tests/test_image_precheck.py`, 215개, 이 PC에서 약 10초): FastAPI 없이 도는 시험과 FastAPI가 있을 때 도는 서비스 시험(없으면 건너뜀)으로 나뉜다. 앞쪽은 (1) 상수 표가 설치된 Pillow의 것과 같은지(TIFF 머리·숫자 형식·하위 IFD 태그, JPEG 마커 표 전체, PNG 청크 종류 식)와, 고친 규칙이 기대는 Pillow의 동작(BYTE 값이 `bytes` 하나로 남는 것, 원소마다 도는 태그 번호, 가리킴 태그가 개수 1로 정의된 것, 압축 청크 처리기와 청크당 1MiB, BMP 정보 머리 크기·RLE 번호·파이썬 디코더)이 참인지, (2) 정상 파일 43개(Pillow의 여러 압축·모드, 줄마다 스트립 3,000개, 16×16 타일, BigTIFF, Exif·GPS 하위 IFD, 팔레트 TIFF, ICC 1.5MB를 가진 JPEG, 스캔 18·6개인 점진 JPEG, EOI 뒤 자료가 붙은 JPEG, 청크·IDAT 조각·압축 청크가 많은 PNG, 30프레임 APNG, RLE8·RLE4 BMP 등)가 통과하고 Pillow로 열리는지, (3) 폭탄 20가지(첫 판의 13가지 + 검토가 찾은 다섯 갈래의 크기 그대로 7가지)가 CPU 2초·파이썬 메모리 8MiB 안에 거절되는지, (4) 상한마다 상한 개수는 통과하고 하나 더는 거절하는지(항목 수는 II·MM·BigTIFF, 스트립·타일 표 네 가지, 숫자 형식 열한 가지, 원소마다 도는 BYTE형 태그 일곱 가지, 하위 IFD 가리킴의 저장 방식 여덟 가지와 값이 여럿인 가리킴 여섯 형식 × 태그 셋, 따라가는 IFD 수, JPEG 세그먼트·머리 길이·쓰레기·채움 바이트·스캔 수·첫 SOS 뒤 세그먼트, PNG 앞·전체·이미지 데이터·압축 청크, RLE BMP 크기), (5) Pillow가 읽는 규칙과의 일치(big-endian BigTIFF, 파일 밖 오프셋, 잘린 표·마커·청크, 알 수 없는 마커, 틀린 청크 종류, 둘째 쪽 이후, 깨진 가리킴을 통과시키고 Pillow도 같게 다루는지. Exif IFD 안의 Interop 가리킴, Pillow가 버리는 앞 항목 뒤의 진짜 가리킴, 한 IFD를 세 가리킴이 가리킬 때 세 번 세는 것, 첫 IFD 자신을 가리킬 때 표를 세는 것을 Pillow가 실제로 푸는 것과 함께 보고, JPEG 엔트로피 자료의 FF 00·세그먼트 안의 FF DA·EOI 뒤 자료를 스캔으로 세지 않는지, RLE가 아니거나 압축 칸이 없는 BMP를 건드리지 않는지), (6) 정상 파일 17개의 잘림 위치(앞뒤 3,000바이트는 전부, 가운데는 7바이트마다)와 무작위로 바꾼 바이트열 5,100개에서 `ImageStructureError` 말고는 예외가 없는지를 본다. 서비스 시험은 줄인 폭탄 13가지(첫 판의 5가지 + 검토가 찾은 다섯 갈래를 줄인 8가지)가 `Image.open`을 부르지 않고 400이 되는지, 20MiB 크기 그대로의 TIFF 스트립 260만 개·`StripByteCounts` 없는 520만 개, JPEG 마커 520만 개, PNG 사설 청크 170만 개가 400으로 끝나는지(둘 다 CPU 2초·파이썬 메모리 16MiB 안), `POST /inspect`·`POST /calibrate`가 400인지, 정상 파일의 화소가 Pillow로 직접 연 것과 같은지, 잘렸거나 깨진 구조 12가지가 400인지, 잘린 파일의 결과가 Pillow만 쓸 때와 같은지를 본다. HEAD 코드에서는 서비스 시험의 폭탄 6건이 모두 실패했고(`_decode`가 예외 없이 끝나고 `/inspect`는 200), 첫 판의 코드에서는 이 판의 새 시험과 고친 시험 51개가 실패했다

## 의존성 취약점 대조

위의 DAST 기록과 따로, 서비스 이미지에 들어가는 의존성(기본 패키지 + `serve` 그룹, `uv.lock`에 고정된 버전)을 공개 취약점 데이터베이스와 대조한 기록이다. CI의 `audit` 작업(`.github/workflows/ci.yml`)이 push와 pull request마다 같은 집합을 pip-audit으로 대조하므로, 이 절에는 그 대조가 경보를 냈거나 손으로 다시 확인한 때를 적는다.

### 로컬 감사 절차
저장소 루트에서 Git Bash로 돌린다. 내보낸 목록은 커밋하지 않는 임시 파일에 둔다.
```bash
out=$(mktemp)
# (1) CI audit 작업과 같은 두 줄: 잠금에서 서비스 집합을 해시와 함께 뽑아, 설치하지 않고 그 버전들을 대조한다.
uv export --frozen --no-dev --group serve --no-emit-project --format requirements-txt -o "$out"
uvx pip-audit@2.10.1 -r "$out" --disable-pip --require-hashes
# (2) 같은 목록을 OSV 데이터베이스로 한 번 더 대조한다(pip-audit의 기본 대조 대상은 PyPI의 취약점 정보다).
uvx pip-audit@2.10.1 -r "$out" --disable-pip --require-hashes -s osv
# (3) 업로드 디코딩을 맡는 Pillow를 GitHub Advisory Database에서 직접 조회한다. 아무 줄도 나오지 않아야 한다.
#     affects의 패키지 이름은 표기를 구분하므로 두 표기를 모두 본다. <버전>은 uv.lock의 pillow 버전이다.
gh api -X GET advisories -f ecosystem=pip -f affects=pillow@<버전> --jq '.[].ghsa_id'
gh api -X GET advisories -f ecosystem=pip -f affects=Pillow@<버전> --jq '.[].ghsa_id'
# (4) 학습용 그룹의 torch·torchvision은 pytorch-cu128 인덱스의 CUDA 빌드(2.11.0+cu128 등)라 PyPI에 없는 판이어서
#     pip-audit이 건너뛴다. OSV API에 이름과 버전(+cu128을 뗀 것)으로 직접 묻는다. 결과의 vulns가 권고 목록이다
#     (권고가 없으면 {}).
curl -s -X POST https://api.osv.dev/v1/query -d '{"package":{"name":"torch","ecosystem":"PyPI"},"version":"<버전>"}'
curl -s -X POST https://api.osv.dev/v1/query -d '{"package":{"name":"torchvision","ecosystem":"PyPI"},"version":"<버전>"}'
```
- (2)와 (3)을 두는 이유: 2026-10-24에 Pillow 12.3.0을 대조했을 때 (1)은 35건을 냈지만 OSV와 GitHub Advisory Database에는 39건이 있었다. (1)에 없던 4건 가운데 하나가 critical인 GHSA-8g5g-8vmr-9782다. 데이터베이스마다 실린 권고가 달라서, CI가 녹색이어도 다른 데이터베이스에만 실린 권고가 있을 수 있다
- (3)의 affects 조회는 이름 표기에 따라 결과가 갈렸다(같은 날 `pillow@12.3.0` 11건, `Pillow@12.3.0` 28건, 겹치는 것 없음)
- (2)는 `--require-hashes`를 주어도 해시가 있는지만 보고 값이 맞는지는 확인하지 않는다는 경고를 낸다. 해시 검증은 (1)이 한다
- (4)를 두는 이유: 학습용 그룹(`train`·`dinomaly`)은 서비스 이미지에 들어가지 않아 CI가 대조하지 않는다. 이 그룹을 손으로 대조할 때 (1)·(2)의 `--group serve`를 `--group train --group dinomaly`로 바꾸면 torch·torchvision은 "Dependency not found on PyPI"로 빠지므로, 이 둘은 (4)로 채운다
- 2026-10-29 추가: CI audit 작업이 (1)에 이어 (2)의 OSV 대조도 돈다. (3)과 (4), 그리고 서비스 집합 밖의 그룹 대조는 여전히 손으로 한다. 잠금 전체를 한 번에 볼 때는 (1)·(2)의 `--no-dev --group serve` 대신 `--all-groups`를 준다
- 2026-11-05 추가: CI audit 작업이 잠금 전체도 대조한다(아래 2026-11-05 절). 그 단계는 환경 표지를 떼어 모든 Python 갈래를 대조하고, torch·torchvision의 로컬 판 표시(`+cu128`)를 떼어 PyPI의 같은 판으로 대조하므로 (4)가 메우던 빈자리까지 덮는다. 바로 위의 `--all-groups` 방식은 환경 표지를 남긴 채 대조하므로 pip-audit을 돌리는 파이썬에 맞지 않는 갈래(예: Python 3.12 이상에서 쓰는 numpy 2.5.3)를 말없이 건너뛴다. (3)은 여전히 손으로 한다
